# HCT-105：历史同步执行说明

本文件说明一次性历史同步工作流的执行边界。它不是日常自动同步的替代品，也不允许直接向内部仓库提交新历史。

## 执行前固定条件

1. GitHub `master` 和内部 `master` 的起点必须由负责人重新核对。
2. 必须提供精确的 `expected_cloud_sha` 与 `expected_github_sha`。
3. 必须输入确认短语 `EXECUTE LEGACY HISTORY TOKEN SYNC`。
4. 工作流先生成最新 dry-run 计划；任意 PR 归属、提交身份、Secret、历史拓扑或 SHA 不一致都会停止。
5. 每个动作执行前读取当前内部 SHA；每次 push 后立即读取并核对目标 SHA。

## 执行过程

工作流按以下顺序处理：

```text
确认短语与两端固定 SHA
  -> 重新读取内部 master
  -> 读取 GitHub PR/提交元数据
  -> 生成按提交身份计划
  -> 逐动作选择对应 Token
  -> 快进 push 一个提交
  -> 校验内部 SHA
  -> 继续下一个动作
  -> 最终核对 GitHub master SHA
```

PR 业务提交与 merge 提交可以使用不同 Token。例如 PR #141 的 `a8fdd9725adb` 使用 `ry12-20` Token，`a885bb68fda7` 使用 `Meyt1n` Token。工作流不会把这两个提交合并成一次使用维护者 Token 的 push。

## 禁止事项

- 禁止 `--force`、`--force-with-lease`、`push --mirror`；
- 禁止重写 Git author 或重新创建相同内容提交；
- 禁止把整个历史统一使用维护者 Token；
- 禁止在运行中修改 GitHub `master`；
- 禁止将 Token 值写入日志、Artifact、Issue 或文档。

如果任一步失败，已成功完成的前序快进动作会保留，工作流会在下一个动作前停止。恢复时必须从当前内部 SHA 重新生成计划，不能直接重复执行旧计划。
