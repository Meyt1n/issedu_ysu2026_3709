## 2. 结论

本地实现和安全验收已完成，结论为“可进入 PR 复核”。Owner 管理边界、非 Owner 的成员/字段/动作/目的/期限校验、隐藏式拒绝、撤权即时生效、授权乐观锁及脱敏审计均有自动化或 Compose 实链证据。HCT-106 的字段裁剪页面和 HCT-107 的生产身份认证仍未完成，不得因本 Story 通过而宣称这两项能力已交付。

## 3. 威胁与控制

| 威胁 | 控制 | 证据 |
|---|---|---|
| 跨家庭读取、写入和 ID 猜测 | 非 Owner 或目标不属于家庭时统一 `404 RESOURCE_NOT_FOUND` | `test_cross_household_reads_writes_and_id_guessing_are_hidden` |
| 角色名称自动扩权 | Owner 只由 `Household.created_by` 判定；非 Owner 必须匹配授权 | ADR-0003、`has_authorized_action` |
| 目的外使用 | 请求携带 `X-Access-Purpose`，与 ASCII 授权目的代码精确匹配 | `test_non_owner_access_requires_the_granted_purpose` |
| 撤权或到期后继续访问 | 每个新请求实时检查 `revoked_at` 和有效期，不使用放行缓存 | 撤权、到期安全测试与 Compose 实链 |
| 并发更新静默覆盖 | `WHERE version = expected_version` 条件更新，冲突返回 `409` | `test_authorization_update_uses_compare_and_swap_versioning` |
| 审计泄露健康正文 | `access_audit` 仅保存授权和决定元数据 | 审计表列断言、Compose `contains_health_body=false` |
| 回滚删除历史审计 | 有审计记录时 migration downgrade 主动拒绝 | `0003_hct102_authorization_security.py` |

## 4. 数据库与 Compose 证据

迁移先在 SQLite 上验证从 `0002_allow_pending_health_events` 的已有授权数据升级，再在隔离 MySQL 8.4 Compose 项目 `hct102verify` 从空库验证。验证过程发现并修复两项跨数据库问题：SQLite 不能直接新增带动态默认值的非空时间列；MySQL 的 Alembic `version_num` 限制为 32 字符。最终 head 为 `0003_hct102_auth_security`。

隔离 Compose 实链结果：

```json
{"authorization_version_created":1,"allowed_events":1,"authorization_version_updated":2,"authorization_version_revoked":3,"post_revoke_status":404,"audit_count":5,"contains_health_body":false}
```

API `/health` 返回 `status=ok`，Web `/health` 返回 `200`。验证完成后已删除 `hct102verify` 的容器、网络和数据卷；其中只有本轮合成家庭、成员、事件和授权，无真实健康数据，不能恢复。

## 6. 回滚与后续边界

- 应用回滚时关闭非 Owner 新访问并保持默认拒绝，不删除或改写 `access_audit`。
- 已有审计的数据库不执行 downgrade，使用前滚修复；空审计环境才允许回退表结构。
- 生产身份仍禁止使用开发头；HCT-107 必须替换 `X-Actor-Id`。
- HCT-106 接入字段级视图时必须复用本次家庭、目的和版本边界，不能只依赖前端隐藏。
- HCT-103 事件补偿与重放不得绕过本次授权检查或把拒绝审计写入健康事件正文。
