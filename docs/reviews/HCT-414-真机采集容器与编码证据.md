## 方法与自我限制

四条互补路径：

1. **设备编码器/容器产物**：`screenrecord` 走与相机录制同一套 MediaCodec 硬件编码 + MP4 muxer，产出真机 MP4 后拉回本地，用 `scripts/hct414_isobmff_probe.py` 解 ISO-BMFF box，并用 OpenCV 交叉验证可解码性。此路径不开摄像头。
2. **相机实拍封装**：`am start -a android.media.action.VIDEO_CAMERA` + `input tap` 驱动 `com.hihonor.camera` 实录，只抽 `moov` 元数据段解析（`mdat` 不出机）；另对照相册里一份既有相机视频做交叉印证。**此路径开启了摄像头**，处置见「隐私与清理」。
3. **WebView 侧类型、解码能力与校验路径**：CDP 接入 App 活动 WebView（不修改任何 App 代码或状态），查 `canPlayType` / `MediaSource.isTypeSupported` / `mediaCapabilities.decodingInfo`，并注入真机字节流重建 `File`，跑 `APP/src/utils/videoInput.ts` 同一套扩展名/MIME 白名单与 `<video>` 元数据探测。
4. **服务端嗅探与上限**：用真机样本直接调 `src/api/app/file_upload.py` 与 `get_settings()`，只读验证，不改服务端。

本机无 `ffprobe` / `ffmpeg` / PyAV，容器结论来自自写的 box 解析器而非第三方探测工具；解析器与 OpenCV 在分辨率、帧数、时长上互相印证（见下表）。判断编解码支持时**必须使用完整 codec 串**：裸 `hvc1` 会被 Chromium 判为不支持，容易得出与实际相反的结论（见 F3 附注）。

## 发现

### F5（阻断级）：混合内容拦截，App 在真机上根本连不上私网 HTTP 服务端

`APP/src/utils/serverUrl.ts` 的 `allowPrivateHttp` 在 `import.meta.env.DEV || MODE === 'android-debug'` 时为真，`isPrivateIpv4` 也明确接受 `172.16–31.x`；`APP/capacitor.config.ts` 的注释同样写着「Android Debug 配合 APP 层私网地址校验开放受控 HTTP 联调」。但在真机上实测，这条路**完全走不通**。

CDP 在 App 活动 WebView 里执行 `fetch('http://172.16.30.29:8000/health')`，拿到的是：

```
Mixed Content: The page at 'https://localhost/#/' was loaded over HTTPS, but requested an
insecure resource 'http://172.16.30.29:8000/health'. This request has been blocked; the
content must be served over HTTPS.
```

`Network.loadingFailed` 的 `blockedReason` 为 **`mixed-content`**。同时 `adb shell nc -z 172.16.30.29 8000` 显示 **TCP 可达**，所以不是网络、不是防火墙、也不是 CORS。

根因链：`capacitor.config.ts` 设了 `androidScheme: 'https'`，页面来源就是 `https://localhost`；Chromium 会拦截 HTTPS 页面发出的明文子请求。而 `APP/src/api/client.ts` 用的是 `globalThis.fetch`（`package.json` 里没有 `@capacitor/http`，`capacitor.config.ts` 里也没有 `plugins` 段），没有走绕过 WebView 策略的原生 HTTP 通道，Android 壳也没有设 `MIXED_CONTENT_ALWAYS_ALLOW`。**结论：APP 层那套私网 HTTP 白名单在当前 Android 构建下是死代码。**

连带后果（两条剩余取证因此做不了）：

1. `ScanView.vue` 的「选择短视频」入口条件是 `videoEntryAvailable = session.dataMode === 'live' && hasCapability('vision-task-video')`。App 连不上任何服务端 → `dataMode` 进不了 `live` → **入口根本不渲染**，真实文件选择器上报的 MIME 无法取证（F2 因此仍是推断）。
2. 真机 App → 服务端的端到端上传同样无法发起，实测 5 只能退化成 PC 发请求。

可能的修法（都要改 `APP/`，**超出 #246 允许修改范围，本增量不动**）：debug 构建改 `androidScheme: 'http'`；或引入 `CapacitorHttp` 走原生请求；或在 Android 壳里设 `setMixedContentMode(MIXED_CONTENT_ALWAYS_ALLOW)`；或让本地 API 提供 WebView 信任的 HTTPS 证书。**release 必须维持 HTTPS-only，修法需按构建模式区分。** 已单独立项跟踪：[#506](https://github.com/Meyt1n/issedu_ysu2026_3709/issues/506)。

### F1（阻断级）：30 s 时长上限与 10 MiB 大小上限在本机相机下互斥

服务端 `vision_video_max_duration_seconds=30` 与 `max_upload_bytes=10 MiB` 同时生效，`APP/src/utils/videoInput.ts` 也镜像了这两个值。但本机相机实测总码率 **15.3 Mbps**（两份独立样本 15.34 / 15.29 Mbps 互相印证），录到 10 MiB 只需 **约 5.5 秒**。

也就是说：**契约允许的 30 秒，在这台真机的默认相机设置下永远录不到**——用户按提示录 10~30 秒，必然撞 `视频大小 … 超过上限 10.0 MB` 而被本地拦下。两个上限在真机上不是互补关系，而是后者把前者压缩到了 5 秒级。这不是实现缺陷，是**契约参数与真机码率不匹配**，需要产品/服务端决定往哪边改（提高大小上限、按码率而非时长约束、或在采集端降档/转码），因此列为阻断项而非本增量可自行修复的问题。

参考量级：按 15.3 Mbps，30 秒需要约 **54.7 MiB**；要在 10 MiB 内装满 30 秒，码率必须压到约 **2.8 Mbps** 以下。

### F2：`File.type` 为空时会被拒，尽管扩展名与内容都合法

`validateMedicineVideo` 在扩展名白名单之后要求 `file.type` 必须命中 `video/mp4 | video/quicktime | video/x-quicktime`。实测中，同一份合法真机 MP4 只要 `File.type` 为空字符串就被拒，提示「视频类型"未知"不受支持」，而 `<video>` 探测明明能读出 5.009 s / 1280×720。部分 Android 文件选择器与第三方相机确实会返回空 MIME，属于真机可复现的误拒风险。

该现象已在 2026-09-02 的移动端兼容性修复中处理：扩展名命中 `.mp4`/`.mov` 且 `File.type` 为空时，继续执行 `<video>` 元数据、大小和时长校验；显式不支持 MIME 仍拒绝。`APP/src/utils/videoInput.test.ts` 已覆盖空 MIME MP4/MOV 和 MIME 大小写归一化。此处结论只证明代码契约，真实文件选择器值与端到端上传仍待真机验收。

### F3：白名单接受 `video/quicktime`，但本机 WebView 不声明支持

`VIDEO_ALLOWED_MIME_TYPES` 含 `video/quicktime` / `video/x-quicktime`，而 WebView 138 对这两个类型 `canPlayType` 与 `MediaSource.isTypeSupported` 都是不支持。上表中 `.mov` 用例之所以通过，是因为 blob 探测走内容嗅探、而样本字节本身是 ISO-BMFF；**真正的 QuickTime 专有编码（如 ProRes）会在探测阶段 fail-closed**，用户看到的是「无法读取视频时长或画面尺寸」。当前 fail-closed 行为安全，但提示语会误导用户以为文件损坏。记录备查，不在本增量处理。

**注意不要把这条推广到 HEVC**：相机产出的 `hvc1` 是**受支持**的（见实测 2 的 `decodingInfo`），只有用裸 `hvc1` 串查询才会误判为不支持。

### F4：容器结构差异

`screenrecord` 产物带 2 条 `mett` 元数据轨、无音轨；相机产物带 1 条 `mp4a` AAC 音轨、无 `mett` 轨，且 `moov` 位于文件**尾部**（`mdat` 使用 64 位 box 长度）。抽帧 worker 若假定「只有一条视频轨」或「`moov` 在前」需要能容忍这两种布局。本次未对 worker 做真机样本联调（见「未覆盖」），仅记录容器事实。

## 复现

```bash
# 1) 真机容器/编码（需已通过无线 adb 连接设备）
adb shell screenrecord --time-limit 5 --size 1280x720 /sdcard/hct414_probe.mp4
adb pull /sdcard/hct414_probe.mp4 && adb shell rm -f /sdcard/hct414_probe.mp4
python scripts/hct414_isobmff_probe.py hct414_probe.mp4

# 2) WebView 侧类型支持与 MOB-149 校验路径
adb shell 'cat /proc/net/unix | grep -o webview_devtools_remote.*'
adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>
curl -s http://127.0.0.1:9222/json/list          # 取 webSocketDebuggerUrl
python scripts/hct414_webview_probe.py <ws-url> hct414_probe.mp4

# 3) 相机实拍封装：只抽 moov，mdat 不出机
adb shell 'am start -a android.media.action.VIDEO_CAMERA'
adb shell 'uiautomator dump /sdcard/ui.xml' && adb shell cat /sdcard/ui.xml   # 定位「录像」tab 与快门
adb shell 'input tap <录像tab>' && adb shell 'input tap <快门>'               # 录制；再点一次停止
# mdat 用 64 位长度定位 moov 起点 = 3246 + mdat_size
adb exec-out "dd if=<VID>.mp4 bs=1 skip=3254 count=8" | xxd -p
adb exec-out "dd if=<VID>.mp4 bs=4096 skip=\$((MOOV/4096))" > cam_moov.bin
adb shell 'rm -f <VID>.mp4 <VID>.mp4.tmp /sdcard/ui.xml'                     # 用完即删

# 4) legacy 相机档位表（仅作对照，不代表相机实际行为）
adb shell cat /vendor/etc/media_profiles.xml

# 5) 服务端嗅探（只读）
cd src/api && python -c "from app.file_upload import _has_ftyp_magic; ..."
```

本机以仓库 `.venv`（Python 3.11.15）代替 `uv`。`scripts/hct414_isobmff_probe.py` 与 `scripts/hct414_webview_probe.py` 随本增量提交，用于满足 NFR-06 可复现；两者只读文件与 WebView，不写入设备也不改 App。
