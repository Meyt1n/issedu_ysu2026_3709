# HomeCare Twin 项目现状、工作总结与后续规划报告

> 项目名称：家健镜 HomeCare Twin
>
> 报告日期：2026 年 8 月 19 日
>
> 报告范围：Web 前端、移动端 App、后端接口协同、测试与工程化交付

## 一、项目概述

HomeCare Twin 是一个面向家庭居家照护场景的教学演示系统。

系统围绕家庭成员、健康事件、用药信息、风险提醒、照护计划和人工复核组织信息，目标是让家庭能够查看已发生的变化、理解风险依据，并完成必要的确认和照护协同。

项目明确坚持“辅助记录、辅助解释、人工确认”的产品边界。

系统不用于诊断、处方、停药、换药或剂量决策，也不提供购药、问诊和广告导流能力。

在数据处理上，项目采用本地优先思路。

健康数据默认不出网，视觉识别结果必须经过多证据校验和人工复核后才能进入后续业务流程。

## 二、当前项目总体状态

当前项目已经从需求与原型阶段进入“多端可运行、关键链路可演示、部分能力持续验收”的阶段。

仓库中已经具备 Web 前端、移动端 App、FastAPI 业务接口、数据库迁移、Docker 编排、自动化测试、视觉识别适配器和相关项目文档。

系统主线已经覆盖家庭健康数据的录入、展示、风险规则计算、照护任务、人工复核和本地知识辅助解释等方向。

但“页面可展示”不等同于“全部生产能力已完成”。

项目中仍有正式认证、移动端真机无障碍验收、部分写回接口、模型发布评估、部署演练等待完成或待最终验证的事项。

当前开发分支为 `feature/jin-123-mob-112-error-feedback`。

最近提交聚焦于移动端 API 错误反馈统一、风险提醒闭环、天气行动卡体验和可访问性对比度修复，说明项目仍在持续迭代收尾和补齐体验细节。

## 三、已完成的工程与技术基础

### 1. Web 前端

Web 端采用 Vue 3、TypeScript 和 Vite 构建。

项目使用统一的 API Client 管理请求、身份头、超时、幂等键和错误解析，避免业务页面重复拼接接口逻辑。

正式 Vue 前端已组织出家庭总览、成员档案、健康计划、视觉扫描、人工复核、用药安全、关系图谱、本地助手、健康大屏、授权管理、知识文档和模型实验室等业务视图。

前端通过共享状态保存当前身份、家庭、成员、会话与提示信息，并以按需加载、骨架屏和统一确认弹窗改善页面切换与操作反馈。

Web 前端还提供主题切换、命令面板、响应式布局和可访问性处理，为演示、管理和后续扩展提供了较完整的应用壳。

### 2. 移动端 App

移动端位于 `APP` 目录，采用 Vue 3、TypeScript、Vite、Vue Router 与 Capacitor 构建。

移动端定位不是 Web 工作台的简单缩小版，而是服务于老人、慢病成员和授权照护者的高频照护入口。

当前已具备今日任务、拍药盒、家人、风险提醒、求助、个人设置、成员详情、提醒详情和无障碍设置等页面。

今日任务支持确认、延期和跳过等核心动作，其中跳过操作要求填写原因，便于保持后续事件记录的可解释性。

移动端具备演示数据模式和家庭服务器联机模式两种数据来源。

演示模式使用明确标注的虚构数据，便于教学展示；联机模式可以调用主仓库 FastAPI 接口，在授权范围内读取家庭、成员、任务、时间线和部分风险数据。

项目已经提供 PWA 清单、Service Worker 和 Capacitor Android 工程，可继续构建 Android 演示包。

### 3. 后端与数据协同基础

后端采用 Python、FastAPI、Pydantic、SQLAlchemy 与 Alembic。

数据库部署场景使用 MySQL，本地调试可以使用 SQLite，以降低开发与演示门槛。

系统采用健康事件追加和状态投影的思路保存变化记录。

该方式有利于追溯“发生了什么、何时发生、由谁确认”，也便于在规则变化后重新生成状态和风险结果。

前端不直接访问数据库、向量库或本地模型服务，而是通过统一业务 API 获取受权限控制的数据和操作结果。

### 4. 视觉识别与人工复核链路

项目已经建立图片质量门控、OCR 优先取证、条码与包装特征辅助、YOLO 辅助定位、候选融合和人工复核相关模块。

视觉识别结果使用 `MATCHED`、`CONFLICT`、`UNKNOWN`、`REVIEW` 等状态表达匹配程度。

图片质量通过只表示“可进入后续识别流程”，不代表药品已识别成功，更不代表已自动写入健康记录。

对于未知、冲突或低置信度结果，系统保留人工复核入口，避免将不确定的识别结果直接作为业务事实使用。

### 5. 测试、构建与部署基础

仓库已覆盖单元测试、契约测试、集成测试、端到端测试、安全测试与浏览器测试等层次。

Web 端配置了 TypeScript 检查、Vitest、Playwright 和 `@axe-core/playwright`，覆盖基础交互、接口联调和部分 WCAG 2.1 AA 自动检查。

移动端已配置类型检查、Vitest、Web 构建和 Android 同步脚本。

项目提供 Docker Compose、Nginx、启动脚本、健康检查、备份恢复和部署说明，具备从本地开发走向演示部署的基础条件。

## 四、当前已交付的业务能力

### 1. 家庭与成员视图

系统可以围绕家庭上下文展示成员、健康事件、用药信息和相关状态。

照护者可见范围以服务端授权过滤为基础，前端不应自行补全未授权字段。

对于不能访问的信息，界面应明确表达“未获授权”，而不是把敏感数据伪装成空数据。

### 2. 风险提醒与照护任务

系统通过确定性规则形成过敏冲突、相互作用、过期、低库存等风险或提醒信息。

风险等级用于提示关注优先级，不输出临床诊断或自主用药结论。

移动端和 Web 端围绕今日任务、风险详情、证据说明和照护动作形成基础闭环。

近期代码已经补充移动端风险提醒安全流程和统一错误反馈，提升了失败状态下的诚实提示能力。

### 3. 视觉录入与复核协同

用户可从前端发起拍摄或上传，并先执行图片质量检查。

质量合格后才可创建视觉任务，后续候选确认仍应由 Web 端人工复核中心处理。

这一职责划分降低了移动端误将自动识别当成最终结论的风险。

### 4. 本地知识与辅助解释

项目提供本地知识入库、检索和模型适配的基础模块。

助手的职责是基于已有事实、规则结果和可引用资料进行解释，而不是替代医疗人员作出诊断或处方判断。

当证据不足、权限不足或依赖不可用时，界面与接口应走受控降级，而不是给出确定性结论。

### 5. 无障碍与适老化尝试

Web 端已对焦点可见性、文字对比度、表单错误关联、状态播报和小屏横向溢出等问题进行修复，并加入自动化可访问性检查。

移动端已实现长辈模式、大字号、高对比度、减少动效、语音播报和较大的触控目标等能力。

这些能力已经形成较好的基础，但 TalkBack、屏幕阅读器和真实设备全路径验收仍需要作为后续重点工作完成。

## 五、阶段性工作总结

### 1. 产品层面

项目已明确 Web 端与移动端的职责边界。

Web 端承担授权配置、人工复核、图谱查看、模型实验室和综合管理等复杂操作。

移动端承担今日任务、拍摄录入、风险查看、家人查看和求助等高频操作。

这种分工避免把需要审慎确认的管理操作压缩到手机端，也更符合照护场景中不同角色的使用方式。

### 2. 前端层面

前端工作已从静态页面制作扩展到状态管理、统一接口访问、错误恢复、加载反馈、响应式布局和可访问性验证。

Vue Web 端负责主要业务流程，React 目录保留为界面风格和教学页面来源，不应被误认为第二套默认运行时。

移动端通过 Data Provider 抽象演示数据与真实接口数据，减少了页面直接依赖某一种数据来源的耦合。

### 3. 协作与工程层面

仓库保留了需求、Story、架构决策记录、测试用例、评审记录和部署文档。

现有工作流要求功能变更关联需求、验收条件、风险、测试与回滚方式，这有助于避免只做界面而缺少可追溯交付依据。

从近期提交看，项目正在针对错误提示、风险闭环、天气行动和可访问性等细节持续补强。

### 4. 需要正视的不足

部分页面和演示数据已经可运行，但并不代表所有生产接口均已稳定完成。

当前开发期身份头 `X-Actor-Id` 不能视为正式认证方案。

移动端的风险“我已知晓”写回、视觉候选确认、完整 TalkBack 验收、正式模型评估和三档部署演练仍需要以真实接口和测试证据作为完成依据。

项目后续应优先完成关键闭环和验收，而不是单纯继续增加页面数量。

## 六、后续工作建议

### P0：应优先完成的事项

#### 1. 完成正式认证与授权边界

需要将开发期身份传递方式替换为正式认证与会话机制。

应明确登录、退出、会话失效、身份切换、权限变化和授权到期后的页面行为。

当授权发生变化时，前端必须清除旧家庭和成员数据，避免残留敏感信息。

#### 2. 补齐高频照护操作的可靠闭环

今日任务的确认、延期、跳过和重试需要保证防重复提交、失败可恢复、操作结果可解释。

成功操作后，任务列表、趋势数据和时间线应在同一轮刷新中保持一致。

对于服务端尚未提供的写回能力，前端应如实提示“暂不能同步”，不能显示为已完成。

#### 3. 完成真机无障碍验收

应在真实 Android 设备上完整验证长辈模式、特大字号、高对比度、减少动效、语音播报、触觉反馈和 TalkBack 焦点顺序。

验收至少覆盖今日任务、拍药盒、风险提醒、求助和个人设置等主要路径。

需要记录设备型号、系统版本、测试步骤、发现的问题和复测结论。

#### 4. 固化发布与回滚流程

应在干净环境中重复执行 Web 构建、移动端构建、Android APK 安装和联机演示。

发布说明应明确版本号、验证范围、演示模式与联机模式的区别、已知限制和回滚步骤。

健康数据、密钥、真实服务器地址和模型权重不得进入仓库或演示包。

### P1：建议在下一阶段推进的事项

#### 1. 建立风险提醒确认回写能力

在后端提供可审计的接口后，可以增加“已知晓”“交由照护者处理”“稍后查看”等受控动作。

每次确认都应记录操作人、时间、风险来源和处理状态，而不是简单隐藏提醒。

#### 2. 完善视觉任务状态与跨端交接

移动端创建视觉任务后，应能看到上传、处理中、等待复核、已确认或需重拍等状态。

当必须转到 Web 端复核时，应给出清晰原因和后续步骤。

Web 端完成复核后，移动端应在授权范围内更新状态，避免用户反复询问识别是否完成。

#### 3. 加强弱网、超时与离线策略

可以增加请求取消、指数退避重试、网络恢复提示和未完成操作草稿。

PWA 离线能力应仅缓存应用外壳与静态资源，不能缓存健康数据或 API 响应。

对不能离线完成的操作，要明确显示当前状态，避免用户误以为数据已同步。

#### 4. 建立统一的前端观测与质量看板

在完成脱敏和同意机制前提下，可记录匿名化的接口失败类型、页面崩溃、关键路径耗时和无障碍缺陷。

指标应服务于问题定位，不应收集可识别的健康内容。

### P2：可规划的扩展方向

#### 1. 本地通知与照护提醒

可在明确权限、隐私和离线规则后，增加本地通知、任务到期提醒和照护者升级提醒。

提醒必须支持关闭、频率控制和等级预算，避免对老人或照护者造成信息负担。

#### 2. 家庭照护协作能力

可增加任务转交、照护备注、处理进度、成员间确认和紧急联系人分级。

所有协作动作都应遵守现有家庭授权范围，不向未授权成员暴露健康细节。

#### 3. 数据导出与家庭归档

可以探索面向教学演示的家庭事件时间线导出、照护任务汇总和人工复核记录归档。

导出前应有二次确认、最小化字段选择、有效期控制和操作审计。

#### 4. 模型实验与质量治理

可继续完善模型版本登记、固定评估集、盲测对比、难例回流和回滚机制。

任何模型迭代都应与训练数据许可、评估记录、适用边界和人工复核率一起管理。

## 八、建议的后续排期

第一阶段建议聚焦认证、授权变化处理、任务写操作防重复、接口错误恢复和 Android 真机基础验收。

第二阶段建议完成风险处理回写、视觉任务跨端状态同步、Web 与移动端联合回归测试。

第三阶段建议完善通知、家庭协作、数据导出和质量指标，同时持续提升无障碍覆盖率。

每一项新增功能开始前，应先补充对应 Story、需求条目、验收标准、测试场景和回滚方式。

对于涉及健康事件、授权、删除、模型与知识库的改动，还应增加安全评审和数据影响说明。

## 九、结论

HomeCare Twin 已经形成了较为完整的家庭居家照护教学演示工程基础。

项目在多端前端、统一接口、事件与投影、视觉取证、风险规则、人工复核、适老化和测试工程等方面均已积累可继续复用的成果。

下一阶段的核心不在于继续堆叠页面，而在于把认证授权、高频照护闭环、真机无障碍、跨端一致性和发布验收做扎实。

只要始终保持数据最小化、人工确认、诚实降级和非医疗诊断边界，项目可以从当前的可演示系统进一步发展为更稳定、更易用、更便于验收的教学实践成果。
