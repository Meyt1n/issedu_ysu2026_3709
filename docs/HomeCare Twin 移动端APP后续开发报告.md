# HomeCare Twin 移动端 APP 后续开发报告

> 调研依据：`Meyt1n/homecare-twin-mobile` 仓库，读取版本 `9aaaa4e6`（2026-08-13）
>
> 目标：以现有“家健镜随身版”为基础，形成面向老人、慢病家庭成员和已授权照护者的移动端交付方案。
>
> 定位：教学演示与家庭照护辅助工具，不用于诊断、处方、停药、换药或剂量判断。

## 一、现有基础与开发方向

目标仓库已经提供一套可运行的移动端 Web 应用和 Android 包装工程，不应从零重建。它与主仓库共用领域术语和 FastAPI API 契约，同时将网页端与移动端分工明确：网页端承担授权管理、人工复核、健康图谱、大屏和模型实验室等重操作；APP 承担每日高频、低步骤的照护动作。

当前代码已有 9 条页面路由：今日、拍药盒、家人、成员档案、提醒、风险依据、求助、我的和无障碍设置。数据层通过 `DataProvider` 隔离演示数据与家庭服务器数据，支持默认演示模式和联机模式，因而后续开发可先在演示数据上验收交互，再接入同一套后端契约。

后续工作的重点不是增加一个独立的数据源，而是把移动端完善为“查看授权信息、完成照护任务、提交可信输入、在紧急情况下快速联系”的随身入口，并把复杂或需要人工判断的操作稳妥地导回网页端。

## 二、推荐技术栈

| 层次 | 采用技术 | 使用方式与原因 |
| --- | --- | --- |
| UI 框架 | Vue 3.5 + TypeScript 5.7 | 与现有代码一致，使用组合式 API、强类型领域模型和按路由懒加载。 |
| 工程构建 | Vite 6 + `@vitejs/plugin-vue` | 现有开发服务器已配置移动设备局域网访问与 `/api`、`/health` 代理。 |
| 页面导航 | vue-router 4（Hash 路由） | 保持静态托管兼容性，并保留现有的页面标题和路由切换语音停止行为。 |
| Android 打包 | Capacitor 8 + Android/Gradle | 使用同一套 Vue Web 代码构建 Android APK，现有应用标识为 `com.homecaretwin.companion`。 |
| 后端通信 | 已有 `ApiClient` + `HttpDataProvider` | 对接主仓库 FastAPI；请求携带身份、访问用途与幂等键，避免页面直接拼接 HTTP 请求。 |
| 演示与联调 | `demoProvider` + `HttpDataProvider` | 演示数据默认本地运行；联机模式接家庭可信域内的服务端，便于分阶段验收。 |
| 离线能力 | PWA Manifest + Service Worker | 缓存应用外壳和静态资源；明确禁止缓存 `/api` 与 `/health`，避免健康数据落入浏览器缓存。 |
| 无障碍与语音 | Web Speech API、CSS 自定义属性、`localStorage` | 支持语音播报、字体缩放、深浅主题、高对比度和减少动效；偏好仅本地保存。 |
| 质量保障 | Vitest 3 + happy-dom + vue-tsc | 保留现有数据适配、会话、无障碍、语音和工具函数单测，并在 CI 中执行类型检查、测试和构建。 |

不建议在当前阶段再引入第二套跨端框架、全局状态库或 UI 组件库。现有 Vue、轻量响应式 store 与手写设计系统已覆盖项目范围；新增依赖应以真实的原生能力缺口或测试需求为依据。

## 三、APP 功能范围

### 1. 今日照护与任务闭环

“今日”页作为默认入口，展示当日照护任务、任务完成进度、近 7 日完成趋势、待关注风险和最近变化时间线。用户可对任务执行确认、延期或跳过：

- 确认、延期和跳过写回 `plan_confirmed`、`plan_deferred`、`plan_skipped` 事件；
- 跳过必须填写原因，延期带明确时长；
- 每次写入生成幂等键，降低移动网络重试造成重复事件的风险；
- 提交后用 Toast、触感反馈和进度状态给出可理解的结果；
- 后续补充下拉刷新、网络失败重试和操作历史入口，确保状态以服务端回执为准。

### 2. 拍药盒与可信录入

拍药盒页已具备“拍摄或相册选择 -> 图片质量检查 -> 创建视觉任务 -> 人工确认”的流程。后续保持以下安全规则：

- 先调用视觉质量检查，质量不通过时只提示重拍原因，不进入识别；
- 质量通过后上传文件并创建视觉任务，候选状态使用 `MATCHED`、`CONFLICT`、`UNKNOWN`、`REVIEW` 四种状态；
- OCR、条码、包装特征和主数据只作为证据来源，任何候选都必须人工确认；
- APP 中只显示任务状态与证据摘要，正式候选确认仍在网页端人工复核中心完成；
- 后续增加相机权限引导、上传进度、断网错误提示、图片大小限制和任务完成通知。

### 3. 家庭成员与授权视图

家人页和成员档案页用于查看成员、已确认时间线、用药清单和可见范围。访问控制由服务端决定，APP 负责如实呈现：

- 家庭所有者可以看到完整视图与授权信息；
- 照护者只显示服务端已授权的成员和字段；
- 未授权信息显示“未获授权”，不能以空值伪装成没有数据；
- 用药、风险和事件请求携带 `X-Access-Purpose` 等上下文并由后端过滤；
- 后续接入正式登录、会话过期处理、授权到期提醒和撤权后的本地状态清理。

### 4. 风险提醒与依据说明

提醒页按严重、较高、一般和提示分级展示风险卡；详情页展示规则版本、风险依据事件和非医疗处置建议。风险由家庭服务端的确定性规则产生，不由 APP 或模型作诊断推断。

后续应补齐风险“已知晓”服务端接口与审计事件。在接口具备前，APP 必须继续如实提示“当前无法回写”，不能把本地按钮状态伪装为已完成处理。

### 5. 紧急求助

求助页提供拨打 `120`、联系预设家庭联系人和语音播报当前重要风险的入口。后续需要补充：

- 联系人编辑校验、号码格式化和一键测试；
- 离线情况下的静态求助信息与拨号可用性验证；
- 不替代急救、问诊或处方，不把风险提醒描述成医疗结论；
- 紧急按钮应始终保持大尺寸、强对比度和可读标签。

### 6. 无障碍与长辈模式

无障碍功能应作为核心交付标准而非附加选项。现有实现已支持长辈模式、标准/大/特大字号、浅色/深色/跟随系统、高对比度、语音播报和减少动效，并将偏好保存到本地。

后续验收至少覆盖：最小 60px 触控目标、文字/图标/颜色三重状态表达、键盘焦点、读屏标签、`prefers-reduced-motion`、375px 小屏布局，以及真实 Android 设备上的语音与拨号行为。

## 四、分阶段实施计划

| 阶段 | 主要交付 | 验收重点 |
| --- | --- | --- |
| 第一阶段：稳定演示与构建 | 演示模式完整可用、APK 可重复构建、类型检查和单测稳定执行 | `npm run check`、`npm run test`、`npm run build` 与 Android debug APK 构建通过。 |
| 第二阶段：家庭服务器联调 | 成员、时间线、任务、风险和视觉质量接口联通；演示造数脚本可重复执行 | 主仓库与 APP 使用同一局域网 API；确认/延期/跳过可见且可审计。 |
| 第三阶段：身份与授权闭环 | 接入正式认证、会话刷新、访问用途校验、撤权与过期处理 | 不同身份只能读取服务端许可范围；越权、撤权、失效会话均有明确界面状态。 |
| 第四阶段：现场可用性 | 相机权限、弱网反馈、通知策略、真实设备无障碍验收 | 重点流程可在 Android 真机完成；网络或服务异常不产生错误成功提示。 |
| 第五阶段：发布准备 | 版本号、签名、隐私说明、崩溃与日志最小化、回归清单 | 仅使用虚构演示数据；不记录密钥和健康数据；发布包可追溯。 |

## 五、接口与数据原则

1. 主仓库 MySQL/事件中心仍是唯一事实来源，移动端不建立平行健康数据副本。
2. 所有写操作使用后端事件语义和幂等键；任务状态由计划事实与最后一个动作事件推导。
3. 本地仅持久化会话配置、无障碍偏好和紧急联系人等最小必要设置，不缓存 API 健康数据。
4. 演示模式中的人员、药品和风险必须显式标注为虚构数据，不能与家庭服务端数据混用。
5. 识别、风险和提醒只提供证据与操作指引，不生成诊断、处方、停药、换药或剂量建议。

## 六、质量与安全门槛

- 每次合并前执行 TypeScript 检查、Vitest 单元测试和生产构建；新增数据适配或状态逻辑必须补充测试。
- 对确认、延期、跳过、上传、风险详情、未授权、接口失败和离线状态编写浏览器/真机验收用例。
- 对关键页面运行无障碍检查并进行读屏与大字号人工验收，不能只依赖视觉截图。
- API 地址配置只允许可信家庭局域网或受控部署地址；开发代理和 Android 明文 HTTP 例外仅用于家庭局域网联调。
- 不将真实健康数据、真实人物信息、模型权重、密钥或访问令牌提交到仓库、日志或演示素材中。

## 七、结论

HomeCare Twin 移动端 APP 已具备可继续迭代的工程底座：Vue 3 + TypeScript 的应用层、Capacitor Android 工程、PWA 外壳、演示/联机双数据提供者、任务和风险的后端适配，以及以长辈模式为核心的无障碍设置均已存在。后续应优先完成正式认证与授权闭环、风险回写接口、真机弱网和相机体验，而不是重复建设页面框架。

最终交付应保持清晰边界：APP 让用户方便地完成每日照护、查看被授权信息、提交可信输入和快速求助；涉及授权管理、候选确认、复杂复核与模型治理的操作继续由网页端承担。
