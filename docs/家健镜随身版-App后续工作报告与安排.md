# 家健镜随身版 App 后续工作报告与安排

> 文档日期：2026-08-15  
> 项目：家健镜随身版 HomeCare Twin Companion  
> 依据：`Meyt1n/homecare-twin-mobile` 的 README、无障碍设计说明、路由、数据提供层、API Client、构建配置及主仓库治理基线。  
> 说明：本文严格区分“已具备”“已联调”和“待完成”。演示数据或界面占位不等同于生产能力；本项目为家庭居家照护教学演示，不用于诊断、处方、停药、换药或剂量判断。

## 1. 工作报告摘要

家健镜随身版的定位已经明确：它不是网页端工作台的简单缩小版，而是面向老人、慢病成员和被授权照护者的高频移动照护入口。网页端继续承担授权管理、人工复核、健康图谱、大屏和模型实验室等较重的管理工作；移动端聚焦“今天要做什么、能否快速录入、有什么需要关注、紧急时如何求助”四类场景。

当前仓库已具备可运行的 Vue 3 H5 应用、Hash 路由、演示数据 Provider、家庭服务器 HTTP Provider、基础 API Client、九个主要页面、PWA 外壳和 Capacitor Android 工程。应用已覆盖今日任务、拍药盒、家人、风险提醒、求助、我的和无障碍设置等核心入口。README 记录显示，家庭/成员列表、时间线、用药清单、部分确定性风险、今日任务写回、图片质量门控和视觉任务创建已经与本地 SQLite 后端进行过联调。

下一阶段的重点不应再只是增加页面数量，而应把“移动端可安全、可理解、可验证地完成高频照护动作”做扎实。具体包括：完善正式鉴权和会话边界、补齐移动端与网页端的任务闭环、完成安卓真机及 TalkBack 验收、明确离线策略、提高真实接口的异常恢复能力，并建立按 Story、分支、PR 和双仓库同步执行的交付节奏。

### 2.2 已实现的用户场景

移动端已有的场景与页面分工较清晰。

- **今日**：查看当日照护任务，执行确认、延期或跳过；查看近七天完成趋势、待关注风险和最近变化。
- **拍药盒**：完成拍摄、图片质量检查、上传和视觉任务创建；识别结果的最终人工确认仍回网页端复核中心完成。
- **家人**：查看当前身份有权看到的成员和字段；未授权字段应以“未获授权”说明，而非假装数据为空。
- **提醒**：按照风险等级查看提醒，展开后阅读出现原因、证据事件和非医疗处置建议。
- **求助**：提供超大求助按钮、联系家人与播报重要提醒的能力；长辈模式下将其保留为主导航入口。
- **我的**：维护无障碍设置、紧急联系人、数据来源和隐私边界说明。

### 2.3 已确认的边界与缺口

当前 README 已如实记录以下限制，后续排期必须以这些限制为输入，而不是把它们视为已经完成的功能。

1. 药盒识别在移动端目前只到“创建视觉任务”；候选确认仍需转到网页端人工复核。
2. 风险“我已知晓”的回写尚无服务端接口，移动端不能伪装成已经写回成功。
3. 正式登录和 PIN 二次确认尚未落地，当前沿用开发期 `X-Actor-Id` 约定，正式鉴权依赖主仓库 HCT-107。
4. 照护者可见范围以服务端过滤为基础；授权明细仅 owner 可读，部分到期信息不展示。
5. 近七天任务完成率根据计划事实和确认事件推导，是近似统计，不应包装为医疗依从性结论。
6. TalkBack/VoiceOver 尚未完成完整遍历验收；iOS 对振动能力的支持也会静默降级。
7. 主仓库投影曾存在药品字段丢失导致部分规则无法触发的缺口，相关修复需以主仓库最终合并和测试证据为准。

## 3. 后续工作目标

后续 App 工作建议以四个目标推进。

### 3.1 目标一：把高频动作做成可靠闭环

老人和照护者在手机上最常做的是查看今天的任务、确认已完成、稍后处理、说明跳过原因、查看重要提醒和联系家人。移动端需要确保这些动作在弱网、重复点击、授权变化和后端暂不可用时仍能给出诚实、清晰且可恢复的反馈。目标不是让手机端承担全部管理工作，而是让少量高频动作做到快速且不容易出错。

### 3.2 目标二：完成移动端与网页端的职责协同

网页端与移动端需要使用同一套家庭、成员、授权、健康事件、风险等级和识别状态语义。移动端遇到需人工复核、授权配置、模型治理等复杂动作时，应能清晰解释“为什么需要转网页端”以及下一步怎么做，而不是展示一个无法完成的按钮。反之，网页端也应能识别移动端发起的视觉任务、计划确认和紧急求助记录。

### 3.3 目标三：以无障碍作为核心验收面

长辈模式不是后期附加的皮肤，而应作为每个新页面的验收条件。标准模式下触控目标不小于 44px，长辈模式下不小于 58px；状态需要同时由文字、图标和颜色表达；特大字号下 320px 宽度不应截断或重叠；高对比和减少动效应覆盖新增组件；语音播报必须能被关闭、被打断且不串台。

### 3.4 目标四：从可演示走向可发布的工程闭环

移动端需建立从功能分支、测试、构建 APK、真机验收、PR 到 GitHub `master` 和内部仓库同步的稳定流程。发布前必须明确数据模式、后端地址、允许的网络范围、已知限制和回滚方案，不能仅因演示数据能跑通就宣称应用已经具备真实家庭部署能力。

## 4. 分阶段工作安排

以下排期按四个迭代阶段安排，每阶段建议一周。实际开始时间应以主仓库 API、鉴权和测试资源可用性为准。每个任务开始前必须绑定 Story，明确 FR/NFR、范围、非目标、数据影响、验收条件、测试命令和回滚方案。

### 第一阶段：联机稳定性与身份边界（第 1 周）

**工作重点**：把已有联机模式从“可以联调”提升到“异常可解释、状态可恢复”。

| 工作项 | 预期产出 | 依赖与验收 |
| --- | --- | --- |
| 联机会话初始化梳理 | 家庭、成员、身份和访问用途的加载状态说明 | 覆盖未填写身份、无家庭、成员为空、服务不可达、授权不足。 |
| API 错误展示统一 | 错误码到用户文案的映射表 | 401、403/404、409、422、网络失败均有不误导的提示。 |
| 请求防重复与刷新策略 | 任务确认、延期、跳过、上传的加载态和刷新规则 | 重复点击不会创建重复事件；失败后可重试。 |
| 后端能力探测 | 联机入口显示服务可用性与能力限制 | 不能把未提供的接口包装成可用功能。 |
| 正式鉴权对接方案 | 与 HCT-107 对齐的接口和页面改造设计 | 在主仓库鉴权契约确定前仅完成适配设计和测试桩，不冒充上线。 |

阶段完成标准：演示模式不受影响；联机模式在网络失败和授权变化时不会遗留旧家庭数据；任务写操作能给出准确成功或失败反馈；相关单元测试和人工联调记录齐全。

### 第二阶段：高频照护闭环与网页端协同（第 2 周）

**工作重点**：强化“今日任务、提醒、拍药盒”三个最高频入口，明确移动端和网页端之间的交接。

| 工作项 | 预期产出 | 依赖与验收 |
| --- | --- | --- |
| 今日任务状态优化 | 任务确认、延期、跳过的完整交互和异常恢复 | 跳过必须填写原因；操作后任务列表、趋势和时间线刷新一致。 |
| 风险提醒闭环 | 风险详情、证据说明、非医疗建议和已知状态展示 | 风险等级只表达确定性规则结果，不输出诊断或用药决定。 |
| “我已知晓”能力评估 | 服务端接口需求或明确的不可用提示 | 未提供后端接口前，页面只能如实说明未写回。 |
| 视觉任务交接 | 创建任务后显示任务状态、复核入口或转网页端说明 | 不让用户误以为药品识别结果已自动入库。 |
| 网页端联动验证 | 移动端写入事件在网页端可看到，网页端复核结果在移动端按授权更新 | 使用虚构数据和可复现脚本进行验证。 |

阶段完成标准：用户可以在手机端完成每日任务的主要动作；所有不能在手机端完成的环节都有明确转交说明；移动端和网页端对同一虚构家庭显示的事实和术语一致。

### 第三阶段：适老无障碍与真机质量（第 3 周）

**工作重点**：把现有无障碍设计从代码层实现推进到可复现的真机验收。

| 工作项 | 预期产出 | 依赖与验收 |
| --- | --- | --- |
| 长辈模式全页面走查 | 320px、标准和特大字号截图与问题清单 | 无截断、重叠、不可点击区域；主导航保持四个大入口。 |
| TalkBack 验收 | Android TalkBack 遍历记录 | 页面标题、按钮名称、焦点顺序、展开状态和动态提示可理解。 |
| 语音播报降级 | 无中文 TTS、首次交互限制和手动播报的验证 | 失败时静默降级并给出适当引导，不阻塞核心操作。 |
| 高对比/减少动效回归 | 三种外观、三档字号、高对比、减少动效组合检查 | 状态不依赖颜色；动效开关对新增动画生效。 |
| 触觉与求助真机测试 | Android 真机和不支持振动设备的对比 | 不支持时不报错；求助操作有清晰的二次确认与安全提示。 |

阶段完成标准：完成至少一台 Android 真机上的核心路径验收；TalkBack、特大字号、高对比和减少动效均有明确测试记录；发现的问题形成可追踪的 Issue 或 Story。

### 第四阶段：发布准备与运行保障（第 4 周）

**工作重点**：形成可重复构建、可安装、可回滚、可说明限制的演示发布包。

| 工作项 | 预期产出 | 依赖与验收 |
| --- | --- | --- |
| APK 构建流水 | 从干净环境构建 debug APK 的记录 | `npm run check`、`npm run test`、`npm run build`、`android:sync` 和 Gradle 构建通过。 |
| PWA 离线审计 | Service Worker 缓存策略验证 | 应用外壳与静态资源可用；`/api`、`/health` 和健康数据不进入缓存。 |
| 环境与配置文档 | 家庭服务器地址、局域网条件、Android 安装步骤、故障排查 | 不写入真实地址、密钥或家庭数据。 |
| 发布说明 | 版本号、已验证范围、已知限制、回滚方式 | 不把未验证能力标为完成。 |
| 双仓库交付 | GitHub PR、Required Checks、自动同步结果 | 仅 GitHub `master` 为合并入口，确认内部仓库哈希一致。 |

阶段完成标准：可以从文档复现 APK 构建和安装；可清楚说明演示模式与联机模式差异；GitHub 合并、检查和内部同步都有可追溯证据。

## 6. 依赖、风险与处理原则

### 6.1 对主仓库的依赖

移动端必须与主仓库共享 API 契约和领域术语。正式鉴权、风险确认回写、药盒候选复核状态、药品投影字段和规则结果都依赖主仓库的后端实现与测试。出现接口缺口时，应记录为依赖或 Issue，不能由移动端用本地假状态掩盖。

### 6.2 数据与隐私风险

仓库不得提交真实姓名、真实家庭健康数据、药品实拍图、密钥、日志、缓存或模型权重。演示数据必须虚构并标注“演示”。PWA 缓存仅可用于应用壳和静态资源，健康数据和 API 响应不得缓存。正式上线前，如需接入崩溃分析、推送或第三方统计，应先完成数据流、数据最小化和授权评审。

### 6.3 适老交互风险

长辈模式下最常见的风险不是功能缺少，而是字号放大后遮挡、点击目标过小、语音无法停止、状态仅靠颜色、对话框焦点丢失或求助按钮误触。因此，每个新增页面必须同时在标准模式和长辈模式中验收，不能只在桌面浏览器的正常字号下验证。

### 6.4 发布风险

Android WebView、不同系统版本、局域网 HTTP、中文路径、TTS 语音包、振动 API 和摄像头权限都会造成设备差异。发布前应至少选择一台低分辨率或小屏 Android 设备和一台常用 Android 设备进行验证，并记录系统版本、网络条件、数据模式和构建版本。

## 7. 交付与验收要求

每一个开发增量应遵循以下最小闭环：

1. 从最新 GitHub `master` 创建功能分支，不直接在 `master` 开发。
2. 创建或关联 Story，写明 FR/NFR、用户价值、范围、非目标、风险、依赖、测试和回滚。
3. 先补测试或可复现验收样例，再完成最小纵向实现。
4. 执行 `npm run check`、`npm run test`、`npm run build`，涉及安卓壳时执行 `npm run android:sync` 和 APK 构建。
5. UI 变更额外执行长辈模式、高对比度、减少动效、键盘焦点和真机无障碍检查。
6. 提交 PR 时如实写明已验证环境、联机或演示模式、数据影响、已知限制和回滚方式。
7. 合并到 GitHub `master` 后检查自动同步的内部仓库提交哈希，不向内部 `master` 直接推送新历史，也不使用强制推送。

## 8. 建议的首个迭代 Backlog

为便于立即启动，建议将以下任务拆成可独立验收的 Story：

1. **MOB-101 联机会话与错误恢复**：统一家庭服务器连接、身份缺失、网络异常、家庭切换和授权不足的状态表现。
2. **MOB-102 今日任务写操作闭环**：确认、延期、跳过的防重复、刷新和错误恢复；覆盖幂等行为。
3. **MOB-103 移动端视觉任务交接**：创建视觉任务后显示状态与网页端人工复核说明，不伪装自动确认。
4. **MOB-104 风险提醒解释与回写缺口治理**：完善风险证据展示，并根据后端接口实际状态决定实现回写或明确提示。
5. **MOB-105 长辈模式与 TalkBack 真机验收**：完成九个页面的特大字号、高对比、减少动效、语音和焦点走查。
6. **MOB-106 Android 构建与演示发布包**：在干净环境构建 APK，形成安装、局域网联机和回滚文档。

## 9. 结论

家健镜随身版已经完成了移动端产品雏形和关键技术骨架，下一阶段的成功标准不是继续堆叠功能，而是让已有的高频照护链路在移动设备上更可靠、更适老、更诚实地反映后端能力。项目应坚持“移动端做高频、网页端做管理与复核”的分工，坚持演示模式和联机模式的真实状态标注，坚持健康数据不缓存、不外泄、不过度解释，并把无障碍、真机验证和双仓库交付纳入每个迭代的完成定义。
