# 过程交付物与评审模板

## 1. 使用规则

培训材料要求每日量化跟踪 Story、代码提交、测试用例、BUG 和评审质量。本文件提供最小模板，团队可录入 GitHub Issue/PR、禅道或课程平台，但编号和状态必须一致。

资料组负责检查完整性，不替开发和测试编造证据。任何“已完成”都必须指向真实提交、测试、评估或验收记录。

## 6. 缺陷记录

```markdown
# [严重度] 缺陷标题

关联需求/Story：

复现步骤：
期望结果：
实际结果：

医疗/隐私/安全影响：
临时缓解：
根因：
修复提交/PR：
回归用例：
状态和负责人：
```

严重度建议：

- S0 阻断：数据泄露、越权、危险医疗建议、核心链路不可用；
- S1 严重：关键功能错误、不可恢复数据问题、稳定复现崩溃；
- S2 一般：有替代路径的功能或兼容问题；
- S3 轻微：文案、样式或低影响体验问题。

## 14. 答辩证据清单

- 项目背景、目标、用户和非目标；
- 团队角色、计划、Story 和进度；
- 需求、架构、业务流程、领域模型和接口；
- 数据来源、数据卡、模型卡和实验曲线；
- 功能演示、失败演示和降级行为；
- 功能、性能、安全、RAG 和模型测试报告；
- AI 使用方式、人工复核、典型提示词和失败案例；
- 每位成员负责的提交、测试、文档和问题解决；
- 部署步骤、已知限制、风险与后续计划。

答辩不能只展示成功页面；至少展示一次低置信度拒识别、无证据拒答或依赖故障降级。

## 15. 与仓库 Office 模板的对应关系

培训交付可继续使用 `doc/09.文档模板/` 中的 Office 模板；本文件用于 GitHub Issue/PR 和日常轻量记录。两种载体使用相同编号并相互引用：

| 过程内容         | Office 模板                     | GitHub/Markdown 对应 |
| ---------------- | ------------------------------- | -------------------- |
| Story 与需求拆分 | `Story列表_模板-v1.2.xltx`      | 第 2 节 Story 卡     |
| 需求基线         | `需求规格说明书_模板-v2.0.dotm` | 需求规格 + 追踪矩阵  |
| 设计评审         | `设计说明书_模板-v1.3.dotm`     | 第 4 节 + ADR        |
| 测试用例         | `测试用例_模板 - V1.2.xltx`     | 第 5 节              |
| 缺陷/问题        | `问题列表_模板-v1.1.xltx`       | 第 6 节              |
| 代码检视         | `代码检视记录_模板-V1.0.xltx`   | 第 12 节 PR 评审     |
| 迭代计划         | `迭代开发计划_模板-v1.1.xltx`   | 八周计划 + 第 13 节  |

正式提交的 Office 文件放入 `doc/` 对应目录；GitHub 记录保存链接、状态和摘要。不得在两个载体中使用不同状态或需求编号。
