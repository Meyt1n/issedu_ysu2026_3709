# HomeCare Twin 开发前必读与 Vibe Coding 工作流

> **强制规则：** 每一位团队成员、每一次 Vibe Coding、每一个 agent 任务，在开始阅读代码、规划方案或修改文件前，必须完整阅读本文件，并根据任务读取对应事实源。本文是团队协作和 agent 协作的共同入口。

> 产品边界：家健镜是本地优先的家庭居家照护教学演示系统，不做诊断、处方、停药、换药、剂量判断，不提供买药、问诊、广告或佣金导流。

## 2. 事实优先级与冲突处理

事实优先级从高到低：

1. 已接受 ADR、迁移、OpenAPI、自动测试和模型登记；
2. 需求、架构、领域模型、隐私和安全基线；
3. 需求追踪矩阵、迭代计划和 Story；
4. Issue、会议记录和个人笔记；
5. AI 对话、外部示例和未经复现的研究结论。

发现冲突时必须报告冲突位置、影响和候选处理方式，由团队评审更新事实源。成员和 agent 都不得默默选择，也不得把聊天内容当作产品事实。

## 3. 每个任务的标准闭环

### 3.1 领取并定义 Story

每个开发增量绑定一个 Story，至少填写：

- FR/NFR 编号和用户价值；
- 范围、非目标、风险等级；
- 负责人、复核人和预计交付时间；
- 输入、输出、异常和 Given/When/Then；
- 允许修改的目录或文件；
- 依赖、数据/模型/规则版本；
- 自动测试、人工验收、部署影响和回滚。

当前一期优先 Story：

- [HCT-101 工程骨架与健康检查](../stories/HCT-101-工程骨架与健康检查.md)；
- [HCT-102 家庭成员与字段授权](../stories/HCT-102-家庭成员与字段授权.md)；
- [HCT-103 健康事件追加与状态投影](../stories/HCT-103-健康事件追加与状态投影.md)。

### 3.2 开始编码

1. 从最新 GitHub `master` 创建任务分支；
2. 检查工作区，保留他人已有修改；
3. 先写失败测试或固定评估样例；
4. 按最小纵向增量实现；
5. 路由不写 SQL，LLM 不承载确定性规则，前端不直连数据库/向量库/Ollama；
6. 同时覆盖正常、边界、依赖故障、未登录、越权和撤权场景；
7. 高风险变更要求合并人完成风险、测试和回滚检查；本仓库不要求额外第二人 approval，merge 即代表人工复核完成。

### 3.3 AI/agent 执行协议

每一次 Vibe Coding 开始时，agent 必须先输出或记录：

- 已阅读本文和对应事实源；
- 绑定的 Story、FR/NFR、用户价值和非目标；
- 计划修改的文件、依赖和风险；
- 验收条件、测试命令和回滚方式。

agent 不得：

- 直接在共享 `master` 上开发；
- 使用 `git add .` 把无关文件、`tmp/`、缓存或本地配置带入提交；
- 使用真实患者/家庭健康数据、未经许可的药品图片或明文密钥；
- 用 Mock、固定回复、截图或 Notebook 冒充完整功能；
- 让模型诊断、开处方、决定停药/换药/剂量；
- 在证据不足、需求冲突或测试无法运行时自行猜测结论。

### 3.4 完成与 PR

本地至少执行：

```powershell
uv run ruff check src/api tests migrations
uv run pytest
npm run check:web
npm run build:web
docker compose config --quiet
git diff --check
```

PR 必须使用 [PR 质量门禁模板](../../.github/pull_request_template.md)，说明关联 Story、变更、测试、数据/隐私影响、部署迁移、回滚和已知限制。只有代码、测试、文档和证据齐全才可请求合并。

## 4. 状态和验收门禁

- `未开始`：只有目标文档，没有实现；
- `进行中`：已有 Story/分支/负责人，尚未完成门禁；
- `待验收`：代码和自动测试已合并，等待业务/安全验收；
- `已验证`：有合并代码、自动测试、人工验收、环境/版本和演示证据；
- `阻塞`：依赖、数据许可、资源或安全条件不满足；
- `不做`：明确排除并记录原因。

状态变更必须同步需求追踪矩阵。没有可定位证据，不得写“基本完成”“应该可用”或“已验证”。

## 5. GitHub、内部仓库和发布

当前 GitHub `master` 是唯一开发和合并入口。内部仓库已与 GitHub 解耦，按[双仓库解耦与独立克隆说明](双仓库解耦与独立克隆说明.md)单独保留和使用：

1. 功能分支推送到 GitHub；
2. PR 合并到 GitHub `master`；
3. 不再由 GitHub Actions 推送、读取或核对内部仓库；
4. 不再要求两个仓库的 `master` 提交哈希一致；
5. GitHub clone 与内部 clone 不互加远端、不互相 push；
6. 禁止从 Git 历史恢复旧的双仓库同步 workflow；如需重新关联，必须先建立新的架构决策并完成评审。

当前项目以 Required Checks 和维护者合并为主要门禁；不要求额外第二人 approval。需要强制保护时，项目负责人应在 GitHub 分支规则中保留 Required Checks，并明确允许维护者在检查通过后直接合并。

## 6. 一句话检查

开发前问自己：

> 我是否知道这个 Story 要解决什么、明确不做什么、改哪些文件、如何证明成功、失败如何回滚，以及合并人将如何完成最终复核？

任何一个答案为“不知道”，先补齐 Story 或发起评审，再开始 Vibe Coding。
