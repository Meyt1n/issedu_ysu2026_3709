# HomeCare Twin 项目全生命周期开发流程

> 文档状态：P0 执行基线
>
> 适用范围：项目负责人、前端组长、后端组长、开发成员、模型负责人、测试/文档负责人和所有 Agent
>
> 时间基线：2026-08-03 至 2026-09-27，共 8 周
>
> 产品边界：教学演示，不用于诊断或治疗；健康数据默认不出网；无购药、问诊、广告或佣金导流

本文件是 HomeCare Twin 从需求冻结到最终交付的统一执行手册。它负责说明“什么时候做什么、由谁交接、用什么证据完成、如何进入下一阶段”。产品、API、数据、安全和测试细节仍以各专项事实源为准；发生冲突时按[开发前必读与 Vibe Coding 工作流](开发前必读与Vibe%20Coding工作流.md)中的事实优先级处理。

## 1. 项目管理对象

项目只使用一条可追踪交付链：

```text
需求 FR/NFR
-> 八周 Milestone
-> GitHub Issue
-> HCT Story
-> 单一任务分支
-> Pull Request
-> CI / Relay 辅助审查 / 合并人复核
-> GitHub master
-> 内部仓库自动同步
-> 自动测试 + 人工演示 + 版本证据
-> 需求追踪矩阵状态更新
```

各对象职责如下：

| 对象 | 唯一用途 | 禁止用法 |
|---|---|---|
| FR/NFR | 定义产品价值和不可妥协的验收边界 | 用聊天记录替代需求 |
| Milestone | 定义一周阶段目标和退出门禁 | 只按日期关闭而不看证据 |
| Issue | 分发 1 至 3 天可完成的任务 | 一个 Issue 混入多个独立目标 |
| Story | 固化范围、非目标、风险、验收、允许修改范围和回滚 | 实现后再倒填验收条件 |
| Branch/PR | 承载一个 Issue 的可审查增量 | 直接修改共享 `master` 或混入他人改动 |
| Evidence | 证明功能、风险、性能和回滚真实成立 | 用截图、Mock、Notebook 或口头说明冒充完成 |
| Traceability | 汇总真实状态和证据链接 | 没有证据就标记“已验证” |

## 2. 团队组织与交接

### 2.1 角色

| 角色 | 主责 | 每日交接对象 |
|---|---|---|
| 项目负责人 / CV 与 LLM 负责人 | 范围、阶段、进度、视觉训练、LLM 微调、风险裁决和最终验收 | 前端组长、后端组长 |
| 前端组长 | 页面状态、交互、API 对接、前端拆分和组内验收 | 项目负责人、后端组长、前端成员 |
| 前端成员 | 页面纵向增量、类型契约、E2E 和可访问性 | 前端组长 |
| 后端组长 | API、数据、授权、事件、规则、集成拆分和组内验收 | 项目负责人、前端组长、后端成员 |
| 后端成员 | 服务、迁移、测试、适配器、部署和可观测性 | 后端组长 |

项目负责人只向两位组长交付阶段目标和当天 Issue。组长负责把 Issue 内的前后端检查项分给组员，但不得把一个 Issue 拆成无法独立验收的“只画页面”或“只建空接口”。涉及 CV/LLM 的接口契约由项目负责人和后端组长共同冻结，前端组长确认展示状态。

### 2.2 决策权限

- 产品范围、医疗边界、数据许可、规则来源、模型发布和阶段退出由项目负责人确认。
- API、Schema、状态机和跨组接口由前后端组长共同确认；有长期影响时创建 ADR。
- Agent 可以实现、测试、审阅和起草文档，不能替团队决定医疗规则、训练授权或验收结论。
- 本仓库不要求额外第二人 approval；维护者执行 merge 代表完成人工复核，但不能省略需求、风险、测试和回滚检查。

## 5. Issue 生命周期

### 5.1 状态

```text
Backlog -> Ready -> In Progress -> In Review -> Done
                \-> Blocked -----------/
```

- `Backlog`：已有阶段和目标，Story/依赖可能未完成。
- `Ready`：需求、Story、依赖、负责人、风险、验收和允许修改范围齐全。
- `In Progress`：已建立个人分支，负责人正在交付。
- `In Review`：已有 PR 和可定位测试证据。
- `Done`：PR 已合并且该 Issue 的验收成立；不等同于整个 FR 已验证。
- `Blocked`：依赖、数据许可、算力、安全或事实冲突阻止继续。

### 5.2 标签与里程碑

每个产品 Issue 至少设置：

- 一个阶段：`stage:w1` 至 `stage:w8`；
- 一个领域：`area:product`、`area:backend`、`area:frontend`、`area:vision`、`area:ai`、`area:data`、`area:security`、`area:devops` 或 `area:test`；
- 一个风险：`risk:R0` 至 `risk:R3`；
- `priority:P0`；
- 对应的 `P0-W1` 至 `P0-W8` Milestone。

### 5.3 Ready 门禁

Issue 只有同时满足以下条件才能领取：

- 唯一 Story ID 和仓库 Story 文件；
- FR/NFR、用户价值、范围和非目标；
- 正常、边界、失败、未授权或依赖故障验收；
- 负责人角色、复核人、前置依赖和预计 1 至 3 天范围；
- 允许修改的文件、测试命令、人工验收和回滚；
- 数据许可、模型/规则/知识版本和网络出口影响已说明；
- 没有待裁决的事实源冲突。

## 6. 每周与每日运行方式

### 6.1 每周节奏

| 时间 | 项目负责人 | 前后端组长 | 成员 | 产物 |
|---|---|---|---|---|
| 周一 | 冻结本周 Milestone 和最多三项关键结果 | 评估依赖、接口和容量 | 阅读 Story、提出阻塞 | 周计划、Ready Issue |
| 周二至周三 | 处理跨组决策和模型任务 | 分发 Issue、接口对齐、Review | 小步实现和测试 | 分支、提交、PR |
| 周四 | 组织集成和失败场景 | 联调、缺陷分级、回滚检查 | 修复、补证据 | E2E、风险记录 |
| 周五 | 阶段验收、演示、范围调整 | 汇总交付和遗留 | 更新文档和复盘 | 周验收、追踪矩阵 |
| 周末 | 只处理明确阻断或下周准备 | 不引入未评审范围 | 不直接改共享 master | 下周 Backlog |

### 6.2 每日任务下发

项目负责人每天只向两位组长发送：Issue 链接、当天唯一目标、接口/模型依赖、验收命令和截止时间。组长在组内明确每人一个可验证增量。当天结束时只汇报：提交/PR、测试结果、阻塞、风险和明日第一步；不使用“差不多”“基本完成”。

在制品限制：每名成员同时最多一个 `In Progress` Issue；每个组同时最多两个未合并功能 PR。出现阻塞时先帮助关闭当前任务，不继续堆新任务。

## 7. Vibe Coding 标准执行

### 7.1 开始前

成员或 Agent 必须先读取 `AGENTS.md`、本文件和 Issue 指定的事实源，然后输出：

```text
Issue / Story / FR-NFR：
用户价值与明确非目标：
当前事实、依赖和冲突：
风险等级与安全边界：
计划修改的文件：
Given/When/Then 验收：
先写的失败测试：
验证命令：
回滚方式：
```

### 7.2 实现中

1. 从最新 GitHub `master` 创建个人任务分支。
2. 检查工作区并保留他人修改，不使用 `git add .`。
3. 先建立失败测试、固定评估样例或可复现缺陷。
4. 实现最小纵向增量，同时更新 API、迁移、Schema 和调用方。
5. 覆盖正常、边界、依赖故障、未登录、越权、撤权和回滚。
6. 视觉、规则、RAG、LLM、数据和模型变更同步对应卡片与版本。
7. 对照范围自审，删除无关改动，不伪造未实现能力。

### 7.3 完成定义

Issue 完成至少需要：实现、自动测试、人工验收步骤、相关事实源更新、已知限制和可执行回滚。页面存在不等于后端完成；接口返回 Mock 不等于模型完成；CI 通过不等于任务完成。

## 8. 分支、PR、Review 与双仓库

```text
git fetch origin master
git switch master
git pull --ff-only origin master
git switch -c feature/<用户名>-<story简述>
```

功能 PR 必须在专用 Issue 字段使用 `Closes #<Issue>`，填写唯一 Story 和 FR/NFR。四项 Required Checks 是：

- `Mandatory development docs`；
- `Backend lint, migration and tests`；
- `Frontend typecheck and build`；
- `Secret scan`。

Relay Review Bot 有 Issue 时辅助检查任务完成度和风险；无 Issue 的维护/会议/纯资料 PR 可跳过。中转服务故障不阻塞 Required Checks，合并人必须执行替代复核。风险建议不自动阻塞，但越权、数据泄露、未确认识别入库、危险医疗判断和不可回滚破坏不得在未理解时合并。

合并后 GitHub Actions 按 PR 作者映射的内部 Token 将同一 SHA 快进同步到内部 `master`。成员只推送 GitHub 个人分支，不直接推两个仓库。同步失败先检查身份、Secret、PR 单一作者和两端 SHA，禁止裸 `--force`。

## 9. 专项交付流程

### 9.1 数据与视觉模型

```text
用途/许可/训练同意
-> 数据卡与脱敏
-> 按实体/日期/设备/会话分组划分
-> 标注复核
-> 固定集冻结和哈希
-> 训练与每类评估
-> 失败样例/未知集/性能
-> 模型卡、批准和回滚版本
```

禁止相邻视频帧跨训练/验证/测试集，禁止用真实未授权家庭数据，禁止只报告最好指标。模型权重不进入 Git 仓库；仓库只保存登记、哈希、配置和报告。

### 9.2 规则与提醒

规则只能来自人工审核的版本化资料。每条规则必须有范围、明确不覆盖、输入确认要求、等级、去重键、预算、有效期、正反例、版本和回滚。LLM 不生成或修改风险等级。严重案例漏报、未确认事实参与规则或 HIGH/URGENT 被预算压制时禁止发布。

### 9.3 RAG 与 LLM

知识入库先记录来源、许可、版本、哈希和权限域；检索前过滤权限。模型输出依次通过 Schema、工具绑定、引用可访问性、事实忠实性、规则不可改写、字段授权、医疗禁止内容、无导流和紧急升级校验。基础模型和 QLoRA 使用同一盲测集；家庭版不得云端回退。

### 9.4 数据库、部署与删除

迁移必须验证空库升级、已有数据升级、索引/外键、失败恢复和前滚/回滚策略。发布前备份事实库并登记代码、迁移、模型、规则、知识和提示词组合版本。删除传播到主库、文件、索引、缓存和可控备份；审计只保留最小证明。

## 10. 状态、证据与阶段验收

需求追踪矩阵是唯一状态汇总入口：

- `未开始`：只有计划；
- `进行中`：有 Ready/In Progress Issue 和负责人；
- `待验收`：代码与自动测试已合并；
- `已验证`：自动测试、人工演示、版本环境和回滚证据齐全；
- `阻塞`：明确的依赖或风险阻止继续；
- `不做`：项目负责人记录原因和影响。

每周退出评审逐项检查：Milestone 内 Issue、合并 PR、自动测试、人工场景、缺陷、风险、数据/模型/规则版本、部署影响、回滚和追踪矩阵。未完成项必须移入下一阶段并说明影响，不能通过修改文字伪装完成。

## 11. 变更、缺陷与事件响应

- 需求变化：更新需求/页面/追踪矩阵，必要时建立 ADR，再调整 Issue；不直接在实现 PR 中扩大范围。
- 普通缺陷：绑定原 Story 或独立 bug Issue，写复现、影响、回归和回滚。
- S0/S1：停止相关合并或发布，隔离版本，保全最小审计，评估影响，回滚并补安全回归。
- 数据/模型/规则事故：停止新推理或发布，冻结版本与证据，不把敏感正文复制到公开 Issue。
- 阶段延期：按缩范围顺序处理并更新依赖链；不可删除安全硬门禁。
