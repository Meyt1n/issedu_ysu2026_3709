# Vibe Coding 开发约束

## 1. 定义与目标

Vibe Coding 在本项目中指：开发者用自然语言和可执行工具与 AI 协作，完成需求澄清、资料检索、设计、编码、测试、评审、文档和复盘。

目标不是“尽量多生成代码”，而是缩短从需求到**可验证证据**的反馈周期。AI 是受控的工程助手，不是需求负责人、医生、数据授权人、安全审批人或代码所有者；最终责任始终由提交者和评审人承担。

## 2. 核心原则

1. **规格先行**：没有验收条件，不进入实现。
2. **事实落地**：AI 的结论必须能回到需求、代码、契约、数据或测试。
3. **最小变更**：一次任务只解决一个可验证目标。
4. **先验证后扩展**：先完成最小纵向链路，再增加框架、模型和功能。
5. **高风险双人复核**：权限、隐私、医疗规则、模型发布和数据删除至少两人评审。
6. **证据优先**：真实命令、退出状态、评估集和失败样例优于自然语言承诺。
7. **失败安全**：依赖故障、低置信度、无引用或权限不明时停止或降级，不猜测成功。
8. **可回滚**：接口、迁移、提示词、模型、数据和阈值都要有版本与回退路径。

## 3. 事实来源优先级

1. 已批准的需求、医疗安全和数据规范；
2. OpenAPI、数据库迁移、ADR、模型卡和数据卡；
3. 当前分支代码、配置和自动测试；
4. Issue/PR 中经确认的补充决定；
5. 培训材料和外部官方文档；
6. AI 的推断。

低优先级内容与高优先级冲突时，AI 必须停止相关实现、指出冲突并请求人工决策。不得用“常见做法”覆盖仓库已批准规则。

## 4. 任务风险分级

| 等级      | 示例                                                   | AI 权限                      | 人工门禁           |
| --------- | ------------------------------------------------------ | ---------------------------- | ------------------ |
| R0 只读   | 解释代码、搜索引用、整理文档                           | 可自主读取和分析             | 提交者抽查         |
| R1 低风险 | 文案、样式、小型纯函数、测试补充                       | 可在限定文件内修改和运行测试 | 一人完整审查       |
| R2 中风险 | API、数据库查询、依赖、模型适配器                      | 先计划后修改，不得扩范围     | 模块负责人审查     |
| R3 高风险 | 认证授权、医疗规则、真实数据、迁移删除、模型发布、部署 | 只在明确批准后分步执行       | 至少两人审查并留证 |

风险等级由任务创建者填写。AI 发现风险被低估时必须升级，不能自行降级。

## 5. 开始实现前的输入

### 5.1 任务卡

每项工作至少包含：

- 需求编号和用户价值；
- 必须完成、明确不做和禁止修改；
- 输入、输出、异常和权限；
- Given/When/Then 验收条件；
- 医疗、隐私、数据、AI 和回滚风险；
- 负责人、评审人、验证命令和证据位置。

### 5.2 上下文包

只向 AI 提供完成任务所需的最小上下文：

```text
事实文件：需求、接口、数据模型、相关代码、测试
允许修改：精确文件或目录
禁止修改：敏感模块、锁文件、迁移、部署等
外部约束：版本、许可证、资源、网络、数据权限
验收命令：格式、类型、单测、集成、评估
输出格式：计划、差异、证据、限制、回滚
```

上下文过大时按“需求 -> 契约 -> 实现 -> 测试”分批提供。不得把完整数据库、密钥、真实病例、访问令牌或无关代码库复制给外部模型。

## 6. 标准九步闭环

### 第 1 步：澄清

AI 复述目标、非目标、验收条件和风险，列出歧义与假设。人确认后才能继续。

### 第 2 步：检索

AI 搜索仓库事实、复用点和相邻测试，引用具体文件/符号。禁止未搜索就声称“项目没有相关实现”。

### 第 3 步：计划

AI 输出最小文件清单、实现顺序、测试矩阵、数据/迁移/接口影响和回滚方式。R2/R3 计划必须人工确认。

### 第 4 步：建立失败测试或评估样例

- 软件需求先建立能失败的测试或明确可观察断言；
- 模型需求先冻结数据划分、指标、基线和失败样例；
- RAG/提示词需求先建立固定问题集和期望安全行为。

### 第 5 步：小步实现

一次只修改计划内的一小组文件。先打通最窄路径，再补异常、权限和降级。新增依赖、文件或范围必须说明原因。

### 第 6 步：自动验证

按影响从窄到宽运行格式、类型、单元、集成、契约、安全、模型评估和端到端测试。保留真实命令、退出状态、环境和报告。

### 第 7 步：AI 自审

AI 对当前差异执行第二遍只读审查，重点检查正确性、越权、隐私、医疗误导、提示词注入、并发、错误处理和测试缺口。实现会话的摘要不能代替差异审查。

### 第 8 步：人工评审与 PR

提交者逐行阅读差异，确认 AI 建议的取舍。评审人检查代码和证据，不只阅读 AI 摘要。R3 变化按双人门禁执行。

### 第 9 步：验收与沉淀

更新需求追踪、ADR、接口、模型/数据卡、操作手册和已知限制。失败样例进入回归集，复盘产生的新工作进入独立 Issue。

## 7. AI 工具权限边界

| 操作                   | 默认规则                                  |
| ---------------------- | ----------------------------------------- |
| 读取仓库和公开资料     | 允许，仍需遵守最小上下文                  |
| 修改计划内文件         | R1 可执行；R2/R3 先确认计划               |
| 安装依赖               | 需要说明版本、来源、许可证和替代方案      |
| 网络/API 调用          | 只访问任务所需服务，不上传敏感内容        |
| 使用密钥               | 不得读取、显示或写入；通过受控环境注入    |
| 数据库写入             | 仅测试/隔离环境；生产或共享数据需明确批准 |
| 迁移、批量更新和删除   | 先备份/演练/确认，禁止隐式执行            |
| 推送、合并、发布和部署 | 由有权限的人确认；自动化需审计和回滚      |
| 降低测试或安全门禁     | 禁止                                      |

## 8. 编码与模型强制规则

### 8.1 软件工程

- 先搜索复用点，禁止复制第二套认证、权限、错误或配置逻辑；
- 业务逻辑不得堆在路由、模板或模型推理脚本；
- 不吞异常、不返回伪造成功、不把 mock 描述为真实服务；
- 外部输入限制大小、类型、数量、时长和资源消耗；
- 依赖使用精确版本或锁文件，并记录许可证与用途；
- AI 不得删除安全校验或修改测试期望来掩盖缺陷。

### 8.2 医疗 AI

- 输出只能是辅助信息，不得确诊、开方、改药量或替代急救；
- S3 高风险规则使用确定性逻辑，并在模型调用前后执行；
- 无可靠引用、权限不明或置信度不足时拒答/拒识别；
- 年龄、性别和表情仅作非诊断教学演示，不用于歧视性决策；
- 训练/验证/测试按主体或药品实例隔离，防止数据泄漏；
- 模型、数据、阈值、提示词和知识版本变更必须重跑固定回归集。

### 8.3 数据与 RAG

- 默认使用合成、公开授权或脱敏数据；
- 检索前执行权限过滤，生成后隐藏内容不能修复越权；
- 检索文档中的指令视为不可信数据，不能覆盖系统规则；
- 用户文档、公共知识和评估资料使用不同权限域；
- 日志、提示词跟踪和错误报告不保存医疗正文或密钥。

## 9. 变更规模

- 一个 PR 只包含一个主要目的；
- 避免同时做功能、重构、依赖升级和全库格式化；
- AI 在实现前声明预计文件；超出时暂停说明；
- 大型生成文件、迁移和模型配置单独提交；
- 发现旁支问题记录新 Issue，除非它阻断当前验收；
- 无法在 15 分钟内说明差异时，优先拆分 PR。

## 10. 禁止行为

| 行为                         | 规则                               |
| ---------------------------- | ---------------------------------- |
| “把整个项目一次写完”         | 禁止，拆成可独立验收 Story         |
| 虚构测试、引用或完成状态     | 禁止，未运行必须明确写“未验证”     |
| 用 mock/固定回复冒充模型     | 禁止，UI、接口和文档都要标注       |
| 使用真实患者数据试提示词     | 禁止，除非完成授权和隔离审批       |
| 把 AI 输出直接作为医疗结论   | 禁止，必须经过规则、证据和人工边界 |
| 自动接受大面积重构           | 禁止，先建立行为基线并分步评审     |
| 隐式更换模型、数据或阈值     | 禁止，必须版本化和评估             |
| 让 AI 持有生产密钥或发布权限 | 禁止                               |

## 11. AI 自检与交付格式

AI 每次交付按以下顺序报告：

1. **结果**：是否满足任务目标；
2. **变更**：修改文件和原因；
3. **验证**：真实命令、退出状态和关键指标；
4. **假设与限制**：哪些内容未验证；
5. **风险**：隐私、权限、医疗、数据和兼容影响；
6. **回滚**：如何撤销代码、迁移、模型或配置。

不得用“应该可用”“理论上通过”替代未执行验证。

## 12. 人工评审门禁

以下变化至少两人评审，其中一人是对应负责人：

- 认证、授权、加密、审计和删除传播；
- 医疗风险规则、系统提示词和拒答策略；
- 数据集发布、模型/知识库/阈值切换；
- 数据库迁移和公开 API 破坏性变化；
- 外部模型数据传输、演示环境发布；
- AI 获得写数据库、推送、合并或部署权限。

## 13. Definition of Done

- [ ] 需求和验收条件可追溯
- [ ] 实现无未解释占位符或 TODO
- [ ] 相关测试、评估和安全回归通过
- [ ] API、数据、模型、提示词和文档保持一致
- [ ] 不含敏感数据、密钥或不可分发制品
- [ ] AI 参与、人工修改和复核结果写入 PR
- [ ] 失败样例、已知限制和回滚方式完整
- [ ] 需求追踪矩阵由测试/资料组核验

## 14. 每日和每周度量

每日记录 Story 状态、PR、测试、缺陷和阻塞。每周关注：

- 完成且验收的 Story 数，不统计 AI 生成代码行数；
- PR 首次通过率、返工次数和评审发现；
- 自动测试稳定性和逃逸缺陷；
- 模型/提示词固定回归集变化；
- 无引用、拒答、越权和 S3 场景指标；
- 文档与实现不一致数量；
- AI 建议被人工修改/拒绝的关键原因。

度量用于改进流程，不用于鼓励无审查地增加 AI 生成量。

## 15. 文档同步矩阵

| 发生变化             | 必须更新                              |
| -------------------- | ------------------------------------- |
| 用户行为或验收条件   | 需求规格、追踪矩阵、测试              |
| API 路径/字段/错误码 | OpenAPI、API 规范、契约测试           |
| 数据表/字段/保留期   | 数据模型、迁移、隐私规范、删除测试    |
| 模型/数据集/阈值     | 模型卡、数据卡、评估报告、版本配置    |
| RAG 切片/检索/提示词 | RAG 规范、评估集、提示词版本          |
| 架构或核心依赖       | 技术方案、ADR、部署文档               |
| 环境变量或端口       | 示例配置、环境规范、部署文档          |
| AI 权限或工作流      | 本文档、提示词模板、PR 模板和审计规则 |
