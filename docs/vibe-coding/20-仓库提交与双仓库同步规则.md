# 仓库提交与双仓库同步规则

> 本文是 HomeCare Twin 的日常 Git 提交和双仓库同步操作入口。
>
> GitHub 是唯一开发、Review、CI 和合并入口；内部云端只接收 GitHub `master` 的同一提交历史。本文是强制协作规则，不能因为本地未启用分支保护而绕过。

## 1. 不可违反的规则

1. 所有进入 `master` 的变更必须先推送到 GitHub 个人分支，再通过 GitHub Pull Request 合并。
2. 禁止任何成员直接向 GitHub `master` 推送，包括会议记录、资料、依赖、维护性和紧急修复。
3. 禁止任何成员直接向内部云端 `master` 推送；普通成员不应向内部云端推送任何分支。
4. 禁止同一工作分支同时推送两个仓库，禁止在内部云端重新提交一份“对应提交”。
5. 一个功能 PR 只绑定一个主要 Issue、一个 Story、对应 FR/NFR 和一个 GitHub PR 作者；PR 内不得混入其他成员的提交身份。
6. PR 作者必须与已登记的 GitHub/Git 提交身份和内部 Token 映射一致。身份不一致时拆分 PR 或先补齐映射，不得借用他人 Token。
7. 禁止裸 `--force`、`git push --mirror`、改写共享 `master` 历史，以及把 Token 写入远程 URL、脚本、日志、Issue 或聊天记录。
8. 合并后只允许 GitHub Actions 自动同步内部 `master`。同步失败时停止人工推送，按本文第 7 节处理。
9. `sync-original-cloud.yml` 只允许调度到专用 `self-hosted/hct-sync` Runner；该 Runner
   可以是 Linux 或 Windows，但不得承接 PR/fork 的不可信代码。Runner 离线或账户 Billing
   受限时，不得把失败伪造为同步成功。

会议记录、纯资料和维护性变更可以不绑定 Issue，但仍必须通过 GitHub PR；“没有 Issue”不是直接推送 `master` 的例外。

|---|---|---|
| GitHub `Meyt1n/issedu_ysu2026_3709` | 开发、Issue、PR、Review、CI、`master` 基线 | 推送个人分支，提交 PR |

推荐本地远端名称为：`github` 指向 GitHub，`cloud` 指向内部云端。执行前必须用 `git remote -v` 确认 URL；如果本地 GitHub 远端仍叫 `origin`，可以暂时把下文的 `github` 替换为 `origin`，但不得配置多个 push URL。

## 3. 标准开发和提交流程

### 3.1 从最新 GitHub `master` 创建分支

```powershell
git status --short --branch
git fetch github --prune
git switch master
git pull --ff-only github master
git switch -c feature/<github-login>-<任务简称>
```

分支类型使用 `feature/`、`fix/`、`docs/`、`test/`、`refactor/`、`chore/` 或 `experiment/`。一个分支只处理一个主要目标；已有未提交改动时不得覆盖、清理或强行切换。

### 3.2 提交前检查

```powershell
git status --short
git diff --check
git diff --stat
git diff -- <明确的文件>
```

只暂存本次任务的明确文件，不使用 `git add .`。禁止提交：真实健康数据、未经许可的图片/视频、`.env`、密钥、Token、模型权重、向量索引、日志、缓存、`tmp/` 和本地备份。

按变更类型执行检查：

- 文档：`git diff --check`；
- 后端/迁移：`uv run ruff check src/api tests migrations`、`uv run pytest`；
- 前端：`npm run check:web`、`npm run build:web`；
- 部署：`docker compose config --quiet`；
- 同步工作流或身份映射：对应 Python 单元测试、YAML/Shell 检查和 `git diff --check`。

检查不能运行时必须在 PR 中说明原因和替代证据，不能写“已通过”代替结果。

### 3.3 提交和推送

```powershell
git add <明确的文件>
git diff --cached --check
git commit -m "<类型>: <简要说明>"
git show -s --format="commit=%H%nauthor=%an <%ae>%ncommitter=%cn <%ce>%nsubject=%s" HEAD
git push -u github <当前分支名>
```

提交消息使用清晰的类型前缀，例如：`feat:`、`fix:`、`docs:`、`test:`、`chore:`。推送命令的目标只能是个人分支，禁止把分支名写成 `master`。

## 4. Pull Request 规则

PR 基准分支必须是 GitHub `master`。功能 PR 必须填写：

- `Closes #<Issue>`、Story、FR/NFR；
- 负责人、复核人、范围和明确非目标；
- Given/When/Then 验收条件；
- 自动测试、人工验收、部署/迁移、风险和回滚；
- 数据隐私、授权、AI/医疗安全和网络出口影响。

PR 提交身份必须满足以下条件：

- PR 作者在身份映射表中；
- PR 内全部提交可归属于该 PR 作者；
- 不把多个成员的提交混入同一个 PR；
- 不通过改写作者、伪造邮箱或借用 Token 绕过检查。

当前仓库的合并门禁为 Required Checks、Review 对话解决、合并人最终核对；本仓库不额外要求第二位 approval。维护者 merge 即代表完成最终人工复核。

## 5. 合并后的 Token 和同步规则

同步归属按“合并 PR 作者”选择 Token，不是按每个 Git commit 单独选择：

1. PR 合并进入 GitHub `master`。
2. Actions 读取内部 `master`，计算尚未同步的 GitHub 第一父链提交。
3. 每个提交必须关联唯一的、已合并到 `master` 的 PR。
4. 身份脚本核对 PR 作者与 PR 内全部提交，并返回该成员的 Token Secret 和内部用户名。
5. 所有待同步 PR 先整体预检；未知作者、混合身份、Secret 缺失或内部历史分叉时，任何 push 都不得执行。
6. 预检通过后，Actions 按第一父链顺序逐个使用对应 PR 作者的 Token 快进内部 `master`。
7. 每次 push 后核对 SHA；最终必须满足：

```text
GitHub master SHA = 内部 cloud/master SHA
```

维护者凭据可能用于读取内部 `master`；这不等于把其他成员的提交归到维护者。真正的内部写入 Token 由 PR 作者映射决定。Actions 日志只允许显示 PR、作者、提交数量和 Secret 名称，不得显示 Token 值。

## 6. 合并后的成员操作

成员只需确认：

```powershell
git ls-remote github refs/heads/master
git ls-remote cloud refs/heads/master
```

两条命令的 SHA 必须一致，并在 GitHub Actions 中确认“同步 master 到原云端仓库”成功。成员不得为了“补同步”而：

- 手动 `git push cloud master`；
- 重新创建同内容提交；
- 删除或重建已合并提交；
- 使用维护者 Token 重推自己的提交。

合并后的 GitHub 功能分支由维护者删除；本地分支只有在没有未提交内容、没有 worktree 占用且确认不再需要时才能删除。

## 7. 异常处理

| 现象 | 正确处理 |
|---|---|
| 同步提示提交没有关联 PR | 说明有人绕过 PR 进入 `master`；停止推送，报告提交 SHA 和 Actions run，不能随便选择 Token |
| 身份未映射或提交身份混合 | 不合并/不重推；补映射、拆分 PR 或更正提交身份后重新走 PR |
| Secret 缺失或权限失败 | 由维护者补齐/轮换 Secret，并重新运行 Actions；不把凭据发给成员 |
| GitHub 与内部 `master` SHA 不一致但可快进 | 由维护者重新运行同步工作流，成员不直接推内部仓库 |
| 两端历史分叉 | 立即停止；维护者备份内部 SHA、确认 GitHub 权威性并按 `--force-with-lease` 恢复，禁止裸 `--force` |
| 内部云端存在需要保留的独立提交 | 不覆盖；先备份并建立人工合并/恢复记录 |
| GitHub Actions 报账户 Billing/付款失败 | 由仓库 Owner 在 `Settings → Billing & licensing` 处理支付方式、额度或账单限制；代码和 Secret 不改变账单状态。Billing 恢复并且 `hct-sync` Runner 在线后，再重新运行同步 |
| `hct-sync` Runner 离线或标签不匹配 | 不切换到未知 Runner；启动/修复专用 Runner 后从 `master` 重新运行，并重新核对两端 SHA |
| Artifact 无法上传或历史配额受限 | 当前工作流已关闭 Artifact 上传；测试、同步前预检、每次 push 后 SHA 核对和最终双端 SHA 以 Actions 日志为准。历史 Artifact 需在 GitHub 页面单独清理，不得删除同步日志 |

一次性历史修复的例外：如果已审计的 PR 分支提交不是当前内部 `master` 的后代，但其后续 merge commit 确实以当前内部 SHA 为第一父链并且 GitHub 是唯一权威来源，`execute-cloud-history-sync.yml` 可以仅对该 PR 分支提交使用精确旧 SHA 的 `--force-with-lease` 暂存。普通提交、merge commit 和未审计分叉不得使用此模式；每个动作必须按对应 Token 执行并在前后校验 SHA，最终两端必须一致。

直接推送到 GitHub `master` 属于流程违规，即使提交内容只是会议记录或资料，也必须记录并修复流程原因。不得通过删除提交、伪造 PR 或改写 Git author 掩盖违规。

## 8. 提交完成检查表

```text
[ ] 工作从最新 GitHub master 分支开始
[ ] 当前工作区已有改动未被覆盖
[ ] 提交身份属于本人且已登记
[ ] 只修改和暂存本次任务文件
[ ] 未包含健康数据、密钥、Token、模型权重、日志或缓存
[ ] PR 基准为 master，功能 PR 已绑定 Issue/Story/FR-NFR
[ ] PR 内没有混合成员提交
[ ] Required Checks 通过，Review 对话已处理
[ ] 合并后 Actions 同步成功
[ ] GitHub master 与 cloud/master SHA 一致
[ ] 个人未直接推送任何内部仓库分支
```
