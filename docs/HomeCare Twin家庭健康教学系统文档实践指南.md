# HomeCare Twin 家庭健康教学系统文档实践指南

> 文档状态：教学资料 / 未开始
>
> 适用范围：本地优先的家庭居家照护教学演示系统
>
> 重要声明：本文用于软件工程、数据治理和产品协作教学，不构成诊断、处方、停药、换药、剂量调整或任何医疗建议。遇到紧急情况，应联系专业医务人员或当地急救服务。

## 1. 文档目的

本文以 HomeCare Twin 为例，整理一套适合实训、项目答辩和团队协作的文档实践方法。

文档关注的不是某一个页面或某一段代码，而是如何把一个复杂的家庭健康数字化项目拆解为可理解、可讨论、可验证的工作单元。

通过阅读和使用本文，团队成员可以逐步理解以下问题：

1. 项目为什么需要明确边界；
2. 什么是事实源，什么只是临时意见；
3. 为什么健康数据需要不可覆盖的事件记录；
4. 如何让识别、规则、提醒和人工确认形成闭环；
5. 为什么文档、测试、风险和回滚必须同时出现；
6. 如何在不泄露敏感信息的前提下完成演示；
7. 如何把一次会议讨论沉淀为后续可执行的任务。

## 2. 项目定位与非目标

HomeCare Twin 是一个本地优先的家庭居家照护教学系统。它帮助家庭成员记录药品、过敏、指标、计划和照护任务的变化，并通过事件、状态、规则和授权视图，让参与者了解“发生了什么、依据是什么、下一步由谁确认”。

这里的“孪生”是家庭健康运营型数字孪生，而不是人体生理模拟器。系统不预测疾病，也不替代医生、药师、护士或急救人员。

系统明确不做以下事情：

- 不做疾病诊断；
- 不生成处方；
- 不决定停药、换药或调整剂量；
- 不根据不完整材料自动确认药品；
- 不把模型生成的文字直接当作医疗事实；
- 不向云端上传默认不应出网的家庭健康资料；
- 不提供购药、问诊、广告或佣金导流；
- 不把演示数据包装成真实临床证据；
- 不把页面截图、固定回复或 Mock 当作完整功能。

明确非目标并不是限制创新，而是让每一次创新都知道自己不能跨过哪条安全边界。

## 3. 核心概念

### 3.1 事件

事件表示某个时间点发生过的事实变化，例如“成员确认了一项过敏信息”“照护者记录了一次服用确认”“系统收到了一份检查报告”。

事件一旦写入，不应通过覆盖原记录的方式修改历史。若事实发生变化，应追加新的更正事件，并保留原事件、操作者、时间和更正原因。

### 3.2 状态

状态是根据事件重建出来的当前视图。状态可以重新计算，也可以在缓存损坏后从事实事件恢复。

事件回答“过去发生了什么”，状态回答“根据目前事件，当前应该显示什么”。二者分开，有利于审计、回滚和发现错误。

### 3.3 证据

证据是支持某个候选事实的可追溯材料，例如人工录入内容、图片中的文字、条码结果、版本化规则或经过授权的教学资料。

证据必须带有来源、时间、版本和适用范围。没有证据时，系统应明确显示未知、缺失或需要复核，而不是用猜测填空。

### 3.4 授权

授权决定谁能看见哪些成员、哪些字段和哪些操作。角色名称不能替代具体授权判断。家庭成员、照护者和管理员都应按照成员级、字段级和操作级权限进行判断。

### 3.5 人工确认

人工确认是把候选结果转为可进入业务事实链的重要门槛。候选结果可以来自 OCR、条码、规则或本地模型，但未经确认不能直接参与高影响的健康状态计算。

## 4. 推荐的系统闭环

一个可复现的教学闭环可以分为以下步骤：

1. 创建教学家庭和演示成员；
2. 录入一项不含真实个人信息的示例事实；
3. 保存输入来源和证据摘要；
4. 运行质量检查或候选识别；
5. 展示匹配、冲突、未知或待复核状态；
6. 由授权人员确认或修正；
7. 追加不可覆盖的健康事件；
8. 根据事件重建成员状态；
9. 运行确定性规则并生成任务；
10. 只向有权限的人展示允许看到的字段；
11. 记录确认、撤销、升级和异常操作；
12. 使用测试和日志证据复盘整个过程。

这条链路的关键不是“自动化越多越好”，而是每一步都能说明输入、输出、失败方式和责任人。

## 5. 文档分类方法

### 5.1 产品文档

产品文档解释用户价值、范围、角色、场景、页面结构和明确不做的能力。它应该帮助非开发人员理解系统，而不是堆砌技术名词。

### 5.2 架构文档

架构文档描述模块边界、数据流、依赖关系、部署形态和故障降级。好的架构文档会说明“为什么这样设计”，而不仅是“用了哪些框架”。

### 5.3 数据与隐私文档

这类文档说明数据类别、来源、保存期限、访问范围、删除传播、备份策略和脱敏方法。健康数据默认按高敏感资料处理。

### 5.4 测试与验收文档

测试文档要覆盖正常路径、边界情况、依赖故障、未登录、越权、撤权、冲突输入、空证据和回滚路径。

### 5.5 会议与复盘文档

会议记录不是聊天记录的简单复制。它应当把讨论整理为结论、待决问题、负责人、截止时间、验收证据和风险。

## 6. 一份合格任务说明应包含什么

建议每个任务至少包含以下字段：

| 字段 | 说明 |
|---|---|
| 任务标题 | 用一句话描述要改变的结果 |
| 用户价值 | 说明谁会因此获得什么帮助 |
| 范围 | 明确这次允许修改的内容 |
| 非目标 | 明确本次不会做的事情 |
| 事实源 | 列出需求、架构、API 或 ADR 来源 |
| 风险等级 | 标记数据、权限、医疗边界和部署影响 |
| 验收条件 | 使用 Given/When/Then 描述可观察结果 |
| 验证命令 | 写出可以实际运行的检查 |
| 人工验收 | 说明需要怎样演示或复核 |
| 回滚方式 | 说明如何撤回变更而不破坏历史事实 |

### 6.1 Given/When/Then 示例

**Given** 一个只包含教学数据的成员档案，并且当前操作者拥有查看授权；

**When** 操作者打开成员详情页；

**Then** 页面只展示授权字段，并且每个候选事实都能看到来源和确认状态。

**Given** 一条识别结果与本地示例主数据冲突；

**When** 系统完成候选融合；

**Then** 结果进入 CONFLICT 或 REVIEW 状态，不得自动写入已确认药品事实。

## 7. 数据治理实践

### 7.1 最小化原则

演示只使用完成任务所必需的数据。姓名可以使用“成员甲”，联系方式可以完全不填写，图片可以使用合成样例，文本可以使用不对应真实个人的占位内容。

### 7.2 来源登记

每份进入知识库或演示目录的资料都应登记来源、许可、版本、摘要和哈希。外部资料不能因为“网上可以看到”就自动拥有再分发权。

### 7.3 删除与撤销

删除请求不仅要考虑主数据库，还要检查文件目录、搜索索引、缓存、导出文件、备份和教学副本。审计记录只保留证明操作发生所需的最小信息。

### 7.4 版本化

规则、知识文档、模型配置、提示词和页面文案都可能影响结果，应当有明确版本。出现争议时，团队需要能够回答“当时使用的是什么版本”。

## 8. 视觉识别与人工复核

视觉识别应当被看作候选生成流程，而不是无条件自动录入流程。推荐的处理顺序如下：

1. 检查图片清晰度、亮度、遮挡和拍摄角度；
2. 进行必要的裁剪、旋转或抽帧去重；
3. 使用 OCR 提取可见文字；
4. 使用条码或其他可验证特征辅助匹配；
5. 对照受控的教学主数据；
6. 标记 MATCHED、CONFLICT、UNKNOWN 或 REVIEW；
7. 由授权人员查看证据并确认；
8. 只把确认后的结果写入业务事实。

当多个证据互相矛盾时，系统应优先展示矛盾，而不是寻找一条“看起来最合理”的结果。拒识是一种正常的安全能力。

## 9. 规则与提醒设计

规则应由人工审核的版本化资料产生，并且能够解释输入、条件、输出、等级、有效期、预算和反例。

一个规则说明可以采用以下结构：

```text
规则编号：RULE-DEMO-001
名称：教学数据的待确认提醒
适用范围：仅适用于已授权的演示成员
输入：存在 REVIEW 状态的候选事实
输出：生成一条普通待确认任务
不覆盖：不改变药物、剂量、用法和诊断状态
等级：普通
确认要求：由本人或授权照护者完成
版本：v1.0
回滚：停用本规则并保留历史事件
```

规则引擎负责确定性判断，语言模型只能解释已有结果或帮助整理信息。模型不得偷偷改写规则等级，也不得在证据之外添加事实。

## 10. 本地助手的安全边界

本地助手的回答应当优先引用可访问的事件、规则和知识版本。回答可以包含事实摘要、来源和下一步确认人，但不能把不确定内容说成确定结论。

建议为助手设置以下输出检查：

- 是否使用了当前用户有权查看的字段；
- 是否给出证据来源或明确说明无证据；
- 是否把规则结果和模型解释区分开；
- 是否出现诊断、处方、停药、换药或剂量建议；
- 是否在紧急风险场景提示联系专业人员；
- 是否包含购药、问诊或广告导流；
- 是否泄露了不必要的个人信息；
- 依赖不可用时是否返回结构化降级结果。

“我不知道”“需要人工确认”和“请联系专业人员”并不是系统失败，而是安全边界被正确执行的表现。

## 11. 权限与隐私演示清单

一次完整的权限演示至少应包含：

1. 管理员查看完整演示家庭；
2. 本人查看自己的授权字段；
3. 照护者只查看被明确授权的成员；
4. 未登录用户无法查看成员数据；
5. 撤销授权后页面和接口都拒绝访问；
6. 越权请求不会通过修改前端参数绕过；
7. 审计记录包含操作者、动作、对象和时间；
8. 导出功能不包含未授权字段；
9. 错误提示不泄露内部数据库或文件路径；
10. 演示结束后可以清理临时数据。

## 12. 测试设计建议

### 12.1 单元测试

验证状态投影、权限判断、规则计算、字段过滤、版本选择和错误映射等确定性逻辑。

### 12.2 契约测试

验证 API 的请求、响应、错误码和字段约束，确保前后端对同一事实有一致理解。

### 12.3 集成测试

验证事件写入、状态重建、规则计算、任务生成和审计记录之间的连接。

### 12.4 安全测试

验证未登录、越权、撤权、伪造身份、敏感字段泄露和默认网络出口限制。

### 12.5 演示回归

固定一组无敏感信息的合成样例，重复演示创建成员、录入候选、人工确认、状态更新、提醒展示和权限切换。

### 12.6 文档检查

文档也应执行链接检查、敏感信息扫描、Markdown 格式检查和 `git diff --check`。文档中的“已验证”必须对应可定位的命令、提交或演示证据。

## 13. 分支、提交与评审

推荐的协作顺序是：

```text
阅读入口文档
  -> 确认 Story、范围、非目标和风险
  -> 从最新 master 创建个人分支
  -> 小步修改并保留他人改动
  -> 运行针对性检查
  -> 提交单一目的的变更
  -> 创建 PR 并填写验收证据
  -> 由维护者完成复核和合并
```

提交信息应能让别人快速理解变更目的。文档提交也不应把缓存、日志、`.env`、模型权重、真实健康资料或个人备份带进仓库。

新增资料类文档时，应优先说明它与既有事实源的关系。如果文档只是教学示例，就明确标记为教学示例，不要让读者误以为它是正式需求、临床指南或已验收能力。

## 14. 文档评审问题清单

评审人可以使用以下问题：

- 读者能否在一分钟内知道本文的目的和边界？
- 文中是否混淆了事实、建议和待决事项？
- 所有“已完成”“已验证”是否有证据？
- 是否引用了可能已经过期的路径、版本或命令？
- 是否包含真实个人信息、密钥或未经许可的图片？
- 是否清楚说明了失败、降级和回滚？
- 是否可能被误解为医疗建议？
- 是否需要同步导航、需求追踪矩阵或 Story？
- 是否存在与已有 ADR、API 或测试事实冲突的说法？
- 新读者能否根据本文完成一次安全的教学演示？

## 15. 典型风险与应对

| 风险 | 可能影响 | 推荐应对 |
|---|---|---|
| 识别结果未经确认就入库 | 错误事实参与后续规则 | 强制 REVIEW 状态和人工确认 |
| 权限只在前端判断 | 越权读取或导出 | API 与数据层再次校验 |
| 规则没有版本 | 无法解释历史结果 | 保存规则版本和生效时间 |
| 模型回答缺少来源 | 用户误信猜测 | 强制引用、拒答和降级 |
| 文档夸大完成度 | 答辩或部署产生误判 | 用证据绑定状态词 |
| 演示使用真实数据 | 隐私和合规风险 | 使用合成数据并清理副本 |
| 回滚覆盖历史 | 审计链断裂 | 追加更正事件，不覆盖原记录 |
| 依赖服务不可用 | 演示流程中断 | 提供结构化降级路径 |

## 16. 实训作业建议

### 作业一：建立一份安全的演示档案

使用“成员甲”“家庭 A”等占位名称创建教学数据，补充一条可追溯的示例事件，并写出它的来源、确认状态和允许查看的角色。

### 作业二：设计一个冲突识别场景

准备两条互相矛盾的合成证据，要求系统显示冲突并阻止自动确认。记录人工复核前后状态变化。

### 作业三：绘制数据流图

从输入、质量门控、候选识别、人工确认、事件、状态、规则、任务和审计八个节点绘制箭头，标注每个节点的输入和输出。

### 作业四：编写权限测试矩阵

分别列出管理员、本人、照护者、未登录用户在查看、修改、确认、导出和撤销授权上的预期结果。

### 作业五：完成一次文档评审

选择一份项目文档，按照本文的评审问题清单逐条检查，记录事实冲突、证据缺口和可以改进的表达。

## 17. 交付前自检表

- [ ] 文档标题、目的、状态和适用范围清楚；
- [ ] 已说明产品边界和明确非目标；
- [ ] 未使用真实健康数据或未经许可的素材；
- [ ] 未写入密码、令牌、私钥或本地绝对路径；
- [ ] 关键结论有对应事实源或标记为教学建议；
- [ ] 识别、规则、助手和权限部分都说明了人工确认边界；
- [ ] 示例内容不会被误认为医疗建议；
- [ ] 链接、代码块、表格和标题格式可正常渲染；
- [ ] 已运行文档相关检查；
- [ ] Git diff 中只有本次任务需要的文件；
- [ ] 提交信息能说明本次变更目的；
- [ ] PR 描述包含验收、风险和回滚说明。

## 18. 结语

高质量的健康软件不只依靠模型能力或页面美观，更依靠清晰边界、可靠事实、可追溯证据、细粒度授权和诚实的状态表达。

在实训项目中，团队可以先从一条合成事件、一条规则和一次权限切换开始，把每一步的输入、输出、责任人和验证方式写清楚。随着系统扩大，再把这些小闭环组合成完整的教学演示。

当一个项目能够清楚回答“谁在什么时候根据什么证据做了什么、结果由谁确认、发生错误如何回滚”时，它才真正具备可协作、可复盘和可持续改进的基础。
