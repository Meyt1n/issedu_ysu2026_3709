## 用户价值

作为家庭照护者，我需要按家庭所在地的服务端业务日查看近 7 天计划完成趋势，以便分辨真实的确认结果、延期与跳过，而不是因浏览器时区、重复回执或计划更新而得到误导性的统计。

## 范围

- 读取家庭接口提供的 IANA 时区 `Household.time_zone`，以该时区切分业务日。
- 使用稳定计划标识折叠 `plan_created` 与 `plan_updated`；更新不新增计划，也不改变原始创建事实。
- 对每个计划仅取服务端时间戳最新的 `plan_confirmed`、`plan_deferred` 或 `plan_skipped` 动作。只有最终动作为确认，且确认发生在该业务日，才计入当日完成。
- 保留窗口前已创建计划在窗口内各日的总数，支持跨午夜、跨月和 DST 日期窗口。
- 缺少家庭时区、计划关联标识或可解析服务端时间戳时显示不可用，不以零柱状图替代未知结果。
- 演示模式使用明确的 `Asia/Shanghai` 时区生成虚构趋势标签；演示数据不代表真实健康事实。

## 非目标

- 不在客户端诊断、处方、停药、换药或判断剂量。
- 不推测缺失的计划关联、最终动作或服务端时区。
- 不缓存健康事件或 API 响应。
- 不改变后端事件写入、幂等键或 Android 真机发布流程。

## 事实与契约边界

联机统计依赖服务端返回 `Household.time_zone`（有效 IANA 时区）以及事件的 `occurred_at`/`created_at` 和 `payload.plan_event_id` 或 `payload.plan_id`。计划创建可用自身事件 ID 作为稳定标识；更新和动作必须显式关联计划。若契约尚未提供这些字段，应用只能呈现“当前不可用或没有可复核数据”，不能把未知解释为 0。真实服务端的时区字段、跨时区回执及 Android 真机证据仍待联机验收。

## 验收场景

1. Given 家庭时区为 `Asia/Shanghai`，When 服务端时间跨越本地午夜，Then 日期归属按上海业务日而非浏览器时区。
2. Given 同一计划先创建后更新，When 渲染趋势，Then 总数只计一次并从原始创建日开始存在。
3. Given 一个计划有重复确认或延期、跳过动作，When 服务端最终动作是确认，Then 只在最终确认所在日计一次；最终动作不是确认时不计完成。
4. Given 计划在窗口前创建而在窗口内确认，When 查看窗口，Then 计划总数从窗口首日可见，完成数仅出现在确认日。
5. Given `America/New_York` 的 DST 切换日，When 生成七日窗口，Then 不重复或遗漏业务日期。
6. Given 时区、稳定关联或时间戳缺失，或权限/API 调用失败，When 页面刷新，Then 显示不可用状态且不伪造零值。

## 测试

- 单元测试覆盖稳定标识折叠、窗口前创建、最终动作、缺失关联/时间戳、时区缺失和 DST 窗口。
- 执行 `npm run check`、`npm run test`、`npm run build`、`npm run android:sync`。
- 联机验收需用两个不同时区家庭、跨午夜回执、成员切换和权限拒绝响应验证；该证据不由本 Story 伪造。

## 风险

- 主服务端未返回有效 `time_zone` 时，联机趋势将不可用，这是防止错误统计的预期降级。
- 事件投影若遗漏计划关联或改变最终动作排序，应用会拒绝显示该趋势，需由服务端修复契约后再验收。
- Android/WebView 的 `Intl` 时区数据需要在目标设备实测，自动化构建不能替代真机证据。

## 回滚

回滚本 Story 对应提交即可恢复原有趋势展示。若服务端尚未交付时区字段，保持当前不可用状态，不恢复按浏览器时区统计的实现。
