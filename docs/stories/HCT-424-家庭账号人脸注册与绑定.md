# HCT-424：家庭账号人脸注册与绑定

关联 Issue：[#280](https://github.com/Meyt1n/issedu_ysu2026_3709/issues/280)

## 用户故事

作为家庭管理员，我希望在取得家庭成员明确同意并完成 PIN 或密码二次确认后，为家庭中的一个账号注册或重新绑定人脸凭证，以便后续由独立的登录切片使用。

## 范围

- 桌面 Web 管理页面支持账号选择、摄像头 2～3 帧动态注册、同意确认、PIN/密码二次确认、重新绑定和删除。
- 服务端只在内存中处理短时上传帧，逐帧执行图片质量门禁、恰好一张人脸校验和动态序列校验；不把单张静态照片作为新凭证。
- 家庭管理员可以为已有成员补绑定本地登录 `actor_id`；同一家庭内账号 ID 不重复，换绑时旧账号的人脸凭证和会话立即失效。
- 数据库只保存 Fernet 加密模板、算法/特征/同意版本、状态和审计元数据。
- 删除、家庭删除或成员删除会清空模板并立即使凭证失效。
- 所有错误、日志、审计和导出均不包含原图、模板、PIN 或密码。

## 非目标

本 Story 不实现人脸匹配、活体检测、登录会话签发或移动端体验；这些能力由 HCT-425 另行设计和验收。

## API

- `GET /api/v1/households/{household_id}/face-credentials`
- `POST /api/v1/households/{household_id}/face-credentials`（multipart）
- `DELETE /api/v1/households/{household_id}/face-credentials/{credential_id}`
- `PATCH /api/v1/households/{household_id}/members/{member_id}/account`

注册接口要求 `consent=true`，并接受 PIN/密码二次确认或已验证且绑定当前会话的 `register_face` step-up challenge。新注册至少需要 2 帧、最多 3 帧动态画面；跨家庭、非管理员、未同意、重复注册、低质量、无人脸、多张人脸和静态重放均拒绝。

2026-08-25：注册接口在处理任何人脸帧之前先完成 PIN/密码/step-up 二次确认；二次确认失败只返回 `CONFIRMATION_FAILED`，不泄露任何 FACE_* 帧处理结果，接口不可被当作人脸质量/活体探测器。换绑（replace）和删除凭证会同时撤销目标账号在本家庭的家庭范围会话（HCT-426 撤销要求），管理员自己的密码会话不受影响。

2026-08-25 根因修复（保存时误报「本地 API 不可用」）：完成引导三帧采集、填好 PIN 与同意后点「完成注册」，前端停在「正在保存…」随后提示「本地 API 服务不可用」。根因是双重的：(1) `register_face_credential` 是 `async def` 路由，却在 asyncio 事件循环上同步执行帧解码、YuNet/SFace 推理以及首次使用时约 37MB SFace ONNX 权重的同步下载（`ensure_face_models`，urllib 逐块读超时 60s、总时长无上限），期间整个 API（含 `/health`）失去响应；(2) 前端 `client.ts` 默认 15 秒超时对人脸 multipart 调用未放宽，`AbortSignal.timeout` 中止后把超时与连接失败一并映射为 `DEPENDENCY_UNAVAILABLE`，`formatError` 显示「本地 API 服务不可用，本次没有改变任何数据」——而服务端此时往往仍在处理并随后提交凭证（用户重试反而得到 409 `FACE_CREDENTIAL_EXISTS`）。修复：后端将注册/1:1 登录/家庭 1:N 登录的重活迁移到专用单线程 `face-pipeline` 执行器（`run_face_pipeline`，同时串行化非线程安全的共享模型实例），应用启动时后台预热已下载权重（`warm_face_models_if_present`，绝不联网）；前端为人脸三条 multipart 调用设置有界 `FACE_REQUEST_TIMEOUT_MS=120s`（不放宽全局默认 15s），新增 `REQUEST_TIMEOUT` 错误码与「可能仍在处理，请刷新确认」文案，使超时不再冒充「API 不可用/未改变数据」；dev 代理空闲超时从 30s 对齐到 240s（低于原值会先掐断慢请求）。回归测试：`tests/contract/test_hct424_face_pipeline_offload.py`（管线必须运行在 `face-pipeline` 线程、注册处理期间 `/health` 必须可响应——旧实现下两者均失败）、`client.test.ts`（超时/断连区分与人脸超时常量）、`store.test.ts`（超时文案不得含「不可用/没有改变任何数据」）。遗留风险：首次注册若冷启动下载 37MB 权重且网络极慢仍可能超过 120s，此时用户会看到「响应超时，可能仍在处理」并可刷新确认结果；维护者可提前运行 `scripts/ensure_face_models.py` 消除冷启动。

2026-08-26 根因修复（Windows 中文路径 ONNX 加载失败，HTTP 500 泄漏本机路径）：修完超时/门禁问题后，Windows 用户注册仍失败，toast 显示「本地 API 处理该请求时出错（HTTP 500: OpenCV ... (-5:Bad argument) Can't read ONNX file: C:\...\多模态医疗\...\face_recognition_sface_2021dec.onnx ...）」。根因：OpenCV 的 C++ 文件加载器在 Windows 上使用 ANSI 窄字符 fopen，`_sface_recognizer`/`_yunet_detector`（`src/api/app/face_credentials.py`）把 `str(path)` 直接传给 `cv2.FaceRecognizerSF_create`/`cv2.FaceDetectorYN_create`，仓库路径含中文时抛 `cv2.error`；该异常不属于路由捕获的 `RuntimeError`/`ValueError`，经 `main.py` 的 generic handler 以裸 HTTP 500 把含完整本机路径的 C++ 报错透出到前端 toast（Haar 级联加载器早有 Unicode 回退，ONNX 加载器没有）。修复：模型路径不再进入任何 OpenCV 文件 API——由 Python 读取 `.onnx` 字节（全平台 Unicode 安全），经 OpenCV≥4.10 的 `create(framework, bufferModel, bufferConfig, ...)` 缓冲重载加载（本机验证缓冲加载与路径加载嵌入完全一致）；加载期 `cv2.error` 统一译为 `RuntimeError("FACE_DETECTOR_UNAVAILABLE")`，注册/1:1/1:N 三条路由再补捕获推理期残余 `cv2.error`，全部映射 503 稳定错误码；`store.ts` 的 503 文案升级为「模型缺失或加载失败 + 本次没有改变任何数据 + `ensure_face_models` 预下载指引」。回归测试：`tests/unit/test_hct424_face_model_unicode_path.py`（真实 YuNet/SFace 从中文目录加载并推理、OpenCV 只收到字节缓冲不收路径、`cv2.error`→稳定错误码、缺失/空模型文件映射）、`tests/contract/test_hct424_face_onnx_error_contract.py`（三条人脸路由遇 Windows 风格 `cv2.error` 返回 503 且响应体不含中文路径/ONNX/C++ 函数名；注册失败后凭证清单为空，「没有改变任何数据」为真）、`store.test.ts`（新 503 文案不透出路径）。用户/运维文档：[docs/demo/人脸凭证录入与登录操作手册.md](../demo/人脸凭证录入与登录操作手册.md)（前置条件、逐步录入/刷脸、Windows 中文路径专节、常见错误速查、验证与回滚）。遗留：建议仓库仍用纯英文路径（Docker 卷挂载等其它工具链对中文路径兼容性不做保证）。

2026-08-25 根因修复（误报 `FACE_FRAME_LOW_QUALITY`）：注册接口此前把面向药盒 OCR 的整图质量门禁（`ai.vision.quality_gate.assess_image`，要求高边缘密度、主体轮廓、整图 Laplacian≥80 和 640×480 下限）误用于摄像头人脸帧。按引导完成 3 帧采集的用户仍会被拒：素墙背景的自拍边缘密度低于 0.005 触发 `NO_TARGET`，常见 16:9 低分辨率摄像头（640×360）不满足 480px 高度下限触发 `IMAGE_TOO_SMALL`，全部坍缩为 `FACE_FRAME_LOW_QUALITY`。修复为人脸专用帧门禁 `ensure_face_frame_quality`（短边≥360、长边≥480、拒绝近全黑/全白帧，`src/api/app/face_credentials.py`）；人脸存在、单人、大小、姿态、清晰度仍由 YuNet 检测 + `assess_face_frame_geometry` 强制。1:1 与家庭 1:N 登录路径同步修复（HCT-425）。前端 `FaceVideoCapture.vue` 增加分辨率过低快速失败与降采样保底（短边不因 960 宽度上限跌破 360）。回归测试：`tests/unit/test_hct424_face_credentials.py`（素墙自拍/低分辨率/黑白帧/过小帧）与 `tests/contract/test_hct425_face_login.py`（真实合成帧流经真实门禁，不再 mock `assess_image`）。
