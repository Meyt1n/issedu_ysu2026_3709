## Given / When / Then（本增量覆盖的部分）

- Given 合成短视频在上限内；When 运行探针；Then 报告返回可复核的分阶段帧数、决定、P50/P95/Max 与夹具哈希。
- Given 视频非法、超限、无法解码或低质量；When 处理；Then 在进入识别前受控拒绝，报告逐条列出期望与实测错误码。
- Given 报告生成；When 检查预算；Then 超过 P95 预算或出现"本应拒绝却被接受"时以非零退出码阻断。
- Given HCT-201 未满足；When 生成报告；Then `release_status` 固定为 `DEMO_ONLY` 并列出阻断项。
- Given 多个视频任务同时到达；When 以 1/2/4 个线程并发运行真实抽帧质量门控；Then 每个请求返回唯一且匹配的 `source_id`，错误数为 0，并记录每级 P50/P95/Max、吞吐和 RSS 高水位。
- Given 并发数、请求数或夹具时长超出探针边界；When 启动探针；Then 立即拒绝参数，不创建无限负载。
- Given 需要多主机容量结论；When 仅运行本探针；Then 明确标记 `multi_host_measured=false`，不得把单机结果宣称为集群容量。
- Given 视频任务带有效质量凭证和适配器回执；When 提交证据；Then 创建一条成员范围内的 `PENDING_REVIEW` 复核任务，且不写入 `HealthEvent`。
- Given 证据路由已创建复核任务；When 再调用融合路由；Then 返回同一 `review_task_id`，补齐融合上下文且不重复创建复核行。
- Given 样本数或预热数越界；When 启动复核交接探针；Then 立即拒绝参数，不创建无限负载。

### 2026-08-28 识别链路后半段 CPU P95（剩余项第 2 条，部分交付）

新增 `scripts/hct414_fullchain_perf.py`，接着视频探针往下测**真实实现**的三级，详见[识别链路后半段 CPU 性能记录](../reviews/HCT-414-识别链路后半段CPU性能记录.md)：

- 条码解码（`LocalBarcodeDecoder`，opencv-contrib `BarcodeDetector`）P95 **6.179 ms**；
- 证据归一化与字段解析（`process_evidence`）P95 **0.123 ms**；
- 候选融合与主数据匹配（`fuse_evidence`）P95 **0.110 ms**；
- **三级合计 P95 6.481 ms**，预算 2000 ms，在预算内；进程 RSS 增量 **28.09 MB**；
- 正常样例终态 `MATCHED` 且 `requires_human_confirmation=true`、`health_event_allowed=false`，匹配成功也不直接写健康事件；
- 四条受控拒绝全部按预期拦在写入健康事件之前：校验位错误 → `REVIEW`/`BARCODE_INVALID_CHECKSUM`、主数据不可用 → `UNKNOWN`/`MASTER_DATA_UNAVAILABLE`、空白图 → 解码 0 候选、名称冲突 → `CONFLICT`/`EVIDENCE_CONFLICT`；
- 夹具是按 EAN-13 模块图案自绘的合成条码（SHA-256 `d8778a84a03512bb…`），不依赖第三方编码库；**渲染参数由实测扫描确定**——opencv 的条码检测对模块宽高比敏感，`module_px=2` 可解码而 3/4/5/6/8 全部失败，这条敏感性对真机照片是潜在风险。

**OCR 推理仍未测**：本机无 `paddleocr`，`LocalPaddleOCR.available=false`。没有硬跑是有意的——缺依赖时实现返回空 token，硬跑只会测到降级路径（≈0 ms），写成「OCR 的 P95」是错的。报告以 `stages_not_measured` 显式披露，单元测试断言该披露必须存在。链路里注入的 OCR token 标为 `synthetic-ocr`，不冒充真实输出。

成本分布提示：条码解码占三级合计 P95 的约 95%，归一化与融合两级不到 0.25 ms。**后半段的真实瓶颈应当是 OCR，而它正是本次缺的那一级**，因此第 2 条不得标记完成。

### 2026-08-28 真机采集容器与编码（剩余项第 3 条，部分交付）

在荣耀 Win `AAP-AN00`（MagicOS 10.0.0 / Android 16 / WebView 138.0.7204.179）上经无线 adb 采集真机证据，详见[真机采集容器与编码证据记录](../reviews/HCT-414-真机采集容器与编码证据.md)：

- **相机实拍封装**（两份独立样本互相印证）：容器 `ftyp` brand **`mp42`**，视频 **`hvc1`（HEVC Main）** 1920×1080@30fps，音频 `mp4a` AAC 48 kHz，`moov` 在文件尾部、`mdat` 用 64 位长度；总码率 **15.3 Mbps**；
- `screenrecord`（同一套 MediaCodec + MP4 muxer）产出 `mp42` / **`avc1` H.264 High 4.2**，另带 2 条 `mett` 元数据轨、无音轨 —— 与相机产物容器布局不同，抽帧 worker 需容忍两种；
- 服务端 `file_upload.py` 的 ISO-BMFF 嗅探与 `.mp4`/`.mov` 幻数校验对真机产物**正常接受**（`ftypmp42`，box 长 24），无需放宽；
- WebView 138 经 `mediaCapabilities.decodingInfo` 判定**可硬件解码相机的 HEVC**（`hvc1.1.6.L93.B0`：supported / smooth / powerEfficient 全为 true），故 MOB-149 的 `<video>` 元数据探测在相机文件上不会失败；注意裸 `hvc1` 串会被 Chromium 误判为不支持；
- **发现一处阻断级契约冲突**：`max_upload_bytes` 10 MiB 与 `vision_video_max_duration_seconds` 30 s 同时生效，但按实测 15.3 Mbps，录到 10 MiB 只需 **约 5.5 秒**、30 秒需要约 **54.7 MiB** —— 契约允许的时长在真机默认设置下永远录不到，需产品/服务端决定调整方向（记录 F1）；
- 另记录一条非阻断风险：白名单接受 WebView 不支持的 QuickTime 类型（F3，不适用于 HEVC）。F2（`File.type` 为空时误拒合法视频）已由移动端扩展名回退修复，真机选择器仍需实测确认。
- **服务端一侧已在活实例上联调**（隔离 SQLite 库 + `vision-task-video` 已声明）：真机 `mp42`/`avc1` 样本 POST `/api/v1/vision-quality/check` 返回 200，`decoded_frames=241 → sampled=4 → selected=1`，`decision=RETAKE`／`reasons=[NO_USABLE_FRAME]`（样本过暗，门控按预期 fail-closed）；四条受控拒绝分别返回 `MEDIA_CONTENT_TYPE_MISMATCH`、`MEDIA_EXTENSION_MISMATCH`、`UPLOAD_MAGIC_MISMATCH`×2。
- **又发现一处阻断级问题（F5）**：`androidScheme: 'https'` 使页面来源为 `https://localhost`，而 `client.ts` 用裸 `fetch`、未引入 `CapacitorHttp`，导致 WebView 以 `blockedReason=mixed-content` 拦截所有指向私网 HTTP 服务端的请求（TCP 层可达，非防火墙非 CORS）。`serverUrl.ts` 那套 `allowPrivateHttp` 私网白名单在当前 Android 构建下**是死代码**。连带后果：App 进不了 `live` → 「选择短视频」入口不渲染 → 真实文件选择器 MIME 与真机端到端上传**都无法取证**。修法都要改 `APP/`，超出本 issue 范围，已单独立项 [#506](https://github.com/Meyt1n/issedu_ysu2026_3709/issues/506) 跟踪。

本条**仍为部分交付**：真实文件选择器上报的 MIME、手机 App 发起的端到端上传、以及相机 HEVC 样本过服务端抽帧**仍未覆盖**（前两条被 F5 卡死），第 3 项不得标记完成，`release_status` 保持 `DEMO_ONLY`。相机取证期间开启过摄像头，产生的视频与误触照片已全部从设备删除（`DCIM/Camera` 文件数回到基线 50），画面数据从未离开手机。
