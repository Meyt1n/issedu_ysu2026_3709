## 用户价值

高风险动作（授权变更、删除）的二次确认真正可用且不可自证：challenge 绑定发起它的登录会话与具体动作，用户用自己已设置的家庭 PIN 完成确认。客户端还能在冷启动或回到前台时主动续验会话，撤权后立即清理界面，而不是等下一次业务请求失败。

## 修复的缺陷

1. **`/auth/pin-challenge` 从来不可能成功。** 它先 `secrets.token_hex(16)` 造了一个从未注册进会话表的随机 token，再交给 `generate_pin_challenge`，而后者第一行就 `validate_session`。带合法 Bearer 的调用固定得到 `401 SESSION_INVALID`（同一 Bearer 访问 `/api/v1/households` 仍 200），因此那句把一次性 PIN 放进响应体的 `return` 位于不可达代码里。
2. **`/auth/pin-verify` 用 query 参数收凭据。** `pin`、`action`、`session_token` 是裸 `str` 形参，FastAPI 解析为 query string，一次性口令与会话 token 会落进请求 URL、反向代理与 APM 日志、浏览器历史。
3. **缺少会话续验端点。** 客户端无法确认会话是否仍然有效，只能等业务请求返回 401，期间界面看起来仍是已登录状态。

## 设计决定：验证用户自己的家庭 PIN

Issue #288 原本写"PIN 通过服务端已确认的带外渠道下发"。本地优先的教学部署没有短信、邮件或推送通道，若服务端生成口令又不许回显，二次确认将永远无法完成 —— 只是换一种失败方式。

因此改为：challenge 只负责**绑定**（会话 + 动作 + 单次 + TTL），**验证**复用 HCT-423 已引入的家庭 PIN（`set_account_pin` 写入的 bcrypt 哈希）。这样响应里没有任何秘密可回显，也不需要新的下发通道，同时仍然满足二次确认的全部要件：用户重新证明持有一个只有本人知道的秘密，且该证明只对一个动作、一个会话、一次有效。

家庭归属：请求可显式带 `household_id`（服务端用 `_actor_belongs_to_household` 校验成员关系，不信任前端选择）；省略时，若该 actor 只在一个家庭配置过 PIN 则由服务端解析，多个则返回 `409 HOUSEHOLD_REQUIRED`，未配置则 `409 PIN_NOT_CONFIGURED`。这让单家庭部署的客户端（含已发布的移动端）无需改动即可工作。

## 接口契约

| 端点 | 请求体 | 成功响应 | 说明 |
|---|---|---|---|
| `POST /api/v1/auth/session` | `{}` + `Authorization: Bearer` | `{ actor_id, expires_at }` | 会话续验；过期/登出/撤销 → 401。不回传任何凭据 |
| `POST /api/v1/auth/pin-challenge` | `{ action, method?, household_id? }` | `{ challenge_id, action, household_id, expires_at }` | **不含任何秘密**；绑定当前会话 |
| `POST /api/v1/auth/pin-verify` | `{ challenge_id, action, method?, code }` | `{ status:"confirmed", challenge_id, action, confirmed_at }` | 一次性；`code` 为该家庭的六位 PIN |

三个端点都要求真实 Bearer 会话：开发期 `X-Actor-Id` 即使在业务端点上启用，也不被二次确认与会话续验接受（`401 SESSION_REQUIRED`）。

错误语义（对齐移动端 MOB-133 已实现的映射）：

- `409 STEP_UP_REPLAY` / `409 STEP_UP_EXPIRED`：challenge 已用或已过期；
- `403 STEP_UP_FAILED`：口令错误、challenge 不存在、会话不匹配、动作不匹配 —— 统一不透出是哪一项，避免探测；
- `429`：沿用既有 `_check_rate_limit` 锁定；口令错误计入锁定但**不消耗 challenge**，用户可在窗口内重试一次手误，同时窗口无法被暴力枚举；
- `409 PIN_NOT_CONFIGURED` / `409 HOUSEHOLD_REQUIRED`：本人可见且可行动的配置问题，不涉及他人信息。

`StepUpGrantRead` 保留 `status:"confirmed"` 字段，让已发布的移动端适配器（MOB-133）无需再发一版即可判定通过。

## Given / When / Then

- Given 已登录会话且该家庭已配置 PIN，When 发起 challenge，Then 响应只含 `challenge_id`、`action`、`household_id`、`expires_at`，不含任何秘密。
- Given 某 challenge，When 另一会话或另一动作提交验证，Then `403 STEP_UP_FAILED`，不透出 challenge 是否存在。
- Given challenge 已使用或已过期，When 再次提交，Then 分别 `409 STEP_UP_REPLAY` 与 `409 STEP_UP_EXPIRED`。
- Given 提交二次确认，When 检查请求形态，Then 凭据只能在请求体；query 参数形态返回 `422`，服务端不再据此判定。
- Given 有效会话，When 调用会话续验，Then 返回 `actor_id` 与 `expires_at`；登出或过期后返回 401。
- Given 只有开发期 `X-Actor-Id`，When 发起二次确认或续验，Then `401`，不降级到开发身份。
- Given 连续输错 PIN 达到上限，When 再次提交（即使口令正确），Then `429`。

## 本地实测（2026-08-20）

`alembic upgrade head` + SQLite + `uvicorn 127.0.0.1:18811`：

```text
POST /auth/session   (Bearer)                  -> 200 {"actor_id":"…","expires_at":1787242568.75}   （原 404）
POST /auth/session   (登出后)                  -> 401
POST /auth/pin-challenge (Bearer)              -> 200 {challenge_id, action, household_id, expires_at}；含 pin 字段: false   （原固定 401）
POST /auth/pin-verify (JSON, 错误 PIN)         -> 403 STEP_UP_FAILED
POST /auth/pin-verify (JSON, 正确 PIN)         -> 200 {"status":"confirmed", …}   （同一 challenge 手误后仍可用）
POST /auth/pin-verify (JSON, 重放)             -> 409 STEP_UP_REPLAY
POST /auth/pin-verify (动作不匹配)             -> 403 STEP_UP_FAILED
POST /auth/pin-verify?pin=…&session_token=…    -> 422   （原 403，即原来会按 query 判定）
POST /auth/pin-challenge (仅 X-Actor-Id)       -> 401
```

关于访问日志：服务端已不再从 query 接受凭据，正常客户端的每一行日志都只有裸路径。仍需说明的是，一个仍把口令拼进 URL 的客户端，其请求行依旧会被 uvicorn 记录 —— 服务端能做的是拒绝据此判定（现为 422），不能阻止客户端自己写什么。

## 安全、隐私与回滚

- 未提交真实健康数据、真实人物信息、密钥、日志或缓存；测试与实测用的账号、家庭与 PIN 全部虚构；
- 日志只记录 actor、action 和 challenge id，从不记录 PIN、密码或会话 token；
- 会话与 PIN 仍是进程内存储（HCT-107 遗留），持久化、轮换与 CSRF 仍是正式部署的阻断项，不在本 Story 范围；
- 回滚：回退本 PR 即恢复到修复前的端点形态；届时应同时关闭客户端的二次确认入口，并撤销未使用的 challenge 与活跃会话。
