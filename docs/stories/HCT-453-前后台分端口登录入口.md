# HCT-453 前后台分端口登录入口

> 2026-08-29 后续决策：HCT-498 / ADR-0008 替代本文“成员以 PIN/人脸为主”的凭据 UI。双端口、不同入口品牌、同一认证 API 和登录后入口锁继续有效，两个入口都只显示正式账号密码表单。

## 1. Story

作为家庭成员，我希望打开「成员前台」的地址就直接看到刷脸 / PIN 的家人登录页；作为家庭管理员，我希望打开「管理后台」的地址看到管理员账号密码登录页。两个入口像成熟系统一样使用**不同端口**，但共用**同一个本地 API、同一套会话与授权真相**，登录后不会把家人误带进后台，也不会把后台界面渲染在前台端口上。

## 2. 方案（成熟产品模式二：同一认证 API + 两个入口面）

- **一个 API（`:8000`）**：密码 / PIN / 人脸登录、会话、HCT-439 owner 门户真相全部不变；本 Story 不新增、不修改任何服务端授权逻辑（仅 CORS 默认值加入后台端口）。
- **两个 Web 入口（同一 Vue 构建产物）**：
  - 成员前台：本地开发 `http://127.0.0.1:5173`，Compose `http://localhost:8080`（`WEB_PORT`）；
  - 管理后台：本地开发 `http://127.0.0.1:5174`（`HCT_ADMIN_WEB_PORT` 可覆盖；本地 Demo 备用端口组为成员 5183 / 管理 5184），Compose `http://localhost:8081`（`ADMIN_WEB_PORT`）。
- **入口模式解析**（`src/web/src/ui/portalEntry.ts`，优先级从高到低）：`?portal=member|admin` 查询覆盖 → `VITE_PORTAL_MODE` 构建/开发 define → Nginx 按监听端口注入的 `window.__HCT_PORTAL_MODE__` → 已知后台端口回退（5174/8081）→ `auto`。
- **auto 模式**：裸 `npm run dev:web`（5173，未设置模式）保持 HCT-439 原单入口行为（按账号角色进门户），供开发调试与既有 e2e 使用；产品入口是上面两个端口。
- **入口锁（UX 锁，非安全边界）**：登录后由 HCT-439 服务端事实（`Household.created_by`、成员绑定）计算真实门户；与入口不匹配时，前端**登出本次会话**并给出跨端指引（成员前台遇管理员 →「去管理后台登录」；管理后台遇成员 →「回成员前台登录」），绝不在错误端口渲染另一门户的界面。授权判断完全在服务端，入口模式不放大任何权限。

## 3. 范围

- `src/web/src/ui/portalEntry.ts` + `portalEntry.test.ts`：入口解析、双端品牌、跨端 URL（支持 `VITE_MEMBER_PORTAL_URL` / `VITE_ADMIN_PORTAL_URL` 显式公开地址，缺省按 5173↔5174、5183↔5184、8080↔8081 换算）、冲突判定与提示文案；管理后台登录只呈现账号密码，成员 PIN / 人脸留在成员前台。
- `src/web/src/store.ts`：`loadHouseholdScope` 计算门户后执行入口锁；命中时登出并设置 `entryConflict`，欢迎页渲染跨端按钮。
- `src/web/src/views/WelcomeView.vue`：成员前台品牌（人脸 / PIN 为主、密码次之）、管理后台品牌（账号密码为主、PIN/人脸标注为家人凭据）、页脚互跳链接、入口冲突提示卡；auto 模式渲染保持不变。
- 开发脚本：`npm run dev:web:member` / `dev:web:admin`（Vite `--mode`，跨平台无需额外依赖）、`scripts/start.sh|ps1 web-member|web-admin`、`HCT_ADMIN_WEB_PORT`。
- Compose/Nginx：`docker/nginx.conf` 两个 server 块（80=前台、81=后台）用 `sub_filter` 注入入口模式，同一镜像同一构建产物；`docker-compose.yml` 暴露 `ADMIN_WEB_PORT:-8081`；`.env.example` 与 API `cors_origins` 默认值加入 `http://localhost:5174` 等。
- 测试：`tests/browser/hct453-portal-entry.spec.ts`（品牌、双向拦截、双向放行）；store/portalEntry 单测。

## 4. 非目标

- 不拆分为两个 Vue 应用或两个 API；不新增第二套登录后端。
- 不修改服务端授权、会话、PIN、人脸契约；不引入仅前端的“管理员”判断（owner 判定仍在服务端）。
- 不改 `APP/` 移动端；不宣称 P0 关闭。
- 既有单入口 e2e（hct417/423/425/439/405 等）继续在 auto 模式运行，不迁移端口。

## 5. 验收标准（Given/When/Then）

1. Given 管理后台入口（5174/5184/8081 或 `?portal=admin`），When 打开欢迎页，Then 显示「家庭管理后台」品牌、只提供账号密码凭据、页脚提供「回成员前台」链接。
2. Given 成员前台入口（5173 显式 member 模式 / 8080 / `?portal=member`），When 打开欢迎页，Then 显示「家庭成员前台」品牌、人脸/PIN 为主、页脚提供「去管理后台」链接。
3. Given 成员前台入口，When 家庭管理员（`created_by`）账号登录成功，Then 会话被登出、显示「这是家庭成员前台入口…」与「去管理后台登录」链接，且不渲染任何后台导航/界面。
4. Given 管理后台入口，When 仅为成员的账号通过密码登录成功，Then 会话被登出、显示「这是家庭管理后台入口…」与「回成员前台登录」链接，且不渲染成员前台界面；PIN / 人脸入口只在成员前台出现。
5. Given 匹配的账号与入口，When 登录，Then 与 HCT-439 行为一致进入对应门户；auto 模式行为与本 Story 之前完全一致。
6. Given Compose `basic` 档，When `up` 后访问 8080 与 8081，Then 同一容器、同一构建产物分别呈现前台/后台入口；API CORS 同时允许 5173/5174/8080/8081。

## 8. 已知限制

- 入口锁是前端 UX 锁：直接调用 API 的脚本不受影响，也不需要受影响——服务端授权（HCT-439/HCT-102）才是安全边界。
- 跨端链接默认按 5173↔5174、5183↔5184、8080↔8081 换算；非默认端口部署需设置 `VITE_MEMBER_PORTAL_URL` / `VITE_ADMIN_PORTAL_URL`（构建期）或接受纯文字端口提示。
- 设备家庭绑定通过同主机 cookie 在双端口共享；两个入口必须使用相同主机名（例如都用 `127.0.0.1`，不能一个用 `localhost`、另一个用 `127.0.0.1`）。该值不是认证或授权凭据，安全边界仍在服务端。
- 一个账号在 A 家庭是管理员、在 B 家庭是成员时，入口锁按“当前选中家庭”的真实门户判定；切换家庭命中不匹配会登出并提示改用另一入口。
- 成员前台入口的“创建家庭”空态仍可用；创建后该账号成为管理员，会被入口锁引导到管理后台完成后续配置。

## 9. 回滚

无数据库迁移、无服务端契约变更。revert 本 Story 提交即可完全回滚到单入口（HCT-439）行为；`docker/nginx.conf` 恢复单 server 块、Compose 去掉 8081 映射即可。API `cors_origins` 默认值回滚不影响既有 5173 客户端。
