# HomeCare Twin 项目全面分析与后续建议

## 1. 项目定位与分析结论

HomeCare Twin 是一个面向家庭居家照护场景的本地优先教学演示系统。它不试图替代诊断或临床决策，而是围绕家庭中真实存在的照护协作问题，建立“事实录入、人工确认、规则分析、任务处理和证据回溯”的信息闭环。项目关注的对象包括药品、过敏史、健康指标、照护计划、家庭成员以及成员间的数据授权关系。

从仓库现有代码、接口说明、页面结构和需求追踪矩阵看，项目已经形成较完整的产品与工程蓝图：前端、后端、视觉识别、规则、知识检索、本地助手、模型治理和移动端均有对应模块或任务。其优势不在于功能数量，而在于对医疗边界、隐私、授权、人工复核和可追溯性的约束较明确。

当前项目更适合定位为“具有较完整业务闭环和较强工程治理意识的教学实践系统”。部分基础能力已经有验证证据，但完整 P0 验收尚未关闭，特别是正式身份认证持久化、真实视觉数据集与模型发布、跨端真实环境验证、性能及人工验收仍需持续推进。因此，对外展示时应准确表述为“已实现或已接入的能力”，避免将进行中任务表述为生产可用功能。

## 2. 用户场景与业务价值

家庭照护的信息往往分散在药盒、检查报告、聊天记录和不同成员的记忆中。即使发现问题，也常常难以回答四个基础问题：最近发生了什么变化、这条提醒为什么出现、谁可以查看这些信息、下一步由谁处理。HomeCare Twin 的设计正是围绕这四个问题展开。

系统以家庭为协作边界。家庭管理员可以维护成员和授权范围，照护者在授权范围内查看已确认的信息并处理任务。药品或文档可经拍照、上传或手工录入进入流程，视觉模块先检查图片质量，再产生 OCR、条码、包装特征等候选证据。候选结果出现冲突、未知或低置信时，应进入人工复核；只有确认或修正后的信息才进入正式健康事件，并参与风险规则、关系图谱、照护计划和证据型问答。

这个流程的业务价值是把“模型给出答案”改为“系统协助形成可审计事实”。对于家庭场景而言，减少错误自动入库比追求一次识别成功更重要；让使用者看到证据、确认状态和责任人，也比单纯显示一个风险标签更有实际意义。

## 3. 功能体系分析

### 3.1 家庭、成员与细粒度授权

项目已将家庭边界和成员级授权作为基础能力。授权不应只判断“是不是家庭成员”，还应同时约束可访问的成员、数据域或字段、允许动作、访问用途和有效期限。撤销授权后，相关数据应立即不可见，并保留必要的脱敏审计记录。

这是项目最重要的业务底座。健康数据具有高度私密性，若成员切换、撤权、跨家庭访问等边界处理不严，后续视觉、助手和大屏等功能都失去可信前提。现有追踪矩阵显示 HCT-102 的授权基础已验证，但正式身份体系、字段视图和部分会话能力仍在推进，说明权限链路需要继续作为发布前最高优先级。

### 3.2 健康事件与状态投影

后端采用“追加健康事件、通过投影计算当前状态”的思路。更正不直接覆盖历史，而是以补偿事件记录原因和新结果。这种设计有利于还原某项事实如何产生、何时被修正，以及某个风险提示使用了哪个版本的数据。

该模式适合家庭照护中的事实变化，例如新增药品、调整计划、补充过敏信息、确认视觉识别结果或撤销错误录入。它也为审计、重放恢复、幂等写入和异步 outbox 处理提供基础。现阶段事件中心仍处于待验收或进行中状态，后续应优先完成 MySQL 与本地环境的一致性回归，并补齐从事件到页面展示的端到端证据。

### 3.3 多证据视觉录入与人工复核

视觉录入不应被理解为普通的“拍照识药”。项目采用质量门控、OCR 优先、条码与包装特征辅助、候选融合和四状态判定的方式处理输入。`MATCHED`、`CONFLICT`、`UNKNOWN` 与 `REVIEW` 等状态让系统能够明确表达识别结论及其不确定性。

这套设计比单模型直接给出药品名称更稳健：低质量图片会提示重拍，冲突或未知结果会要求人工复核，原始预测、修正前后差异和修正原因需要保留。当前已有合成数据和部分接口、网页闭环的实现与测试，但正式固定数据集、数据来源审批、独立评估和模型发布仍受阻。这意味着视觉能力可用于演示和工程验证，不能以真实药品识别准确率或临床可靠性作出承诺。

### 3.4 风险规则、照护计划与环境行动

系统把风险判断交给版本化的确定性规则，可覆盖过期、临期、低库存、重复成分、过敏风险及部分环境条件。规则输出应包含等级、触发依据、规则版本、处理状态和升级对象。普通提醒需要预算与合并策略，较高等级提醒则应进入更明确的确认或升级路径，以减少告警疲劳。

照护计划模块承接规则结果，支持确认、延期、跳过和照护升级等动作。系统需要记录操作人、时间和原因，避免“提醒已处理”成为无法验证的页面状态。天气等外部依赖应采用白名单、缓存、限速和离线降级；环境行动卡只能提示一般性照护行动，不能修改药物或剂量。当前相关模块多数仍在实现或待验收阶段，完整的严重风险零漏报验证是关键缺口。

### 3.5 本地助手、知识检索与模型治理

本地助手的正确角色是解释，而不是决策。它应先调用白名单工具获取已授权的家庭事实、规则结果和知识文档，再附带可追溯引用生成说明；证据不足、权限不足或本地模型离线时，应直接说明限制并降级。项目明确拒绝输出停药、换药和剂量决定，也不提供购药、问诊和广告入口。

模型实验室、困难样本池、模型卡、版本登记和回滚演练体现了项目对 AI 治理的重视。当前训练入口、部分模型登记和教学页面已经存在，但真实训练数据批准、独立盲测、正式模型发布和完整安全验收尚未完成。后续应坚持“未批准数据不训练、未独立评估不发布、无证据不回答”的门禁原则。

### 3.6 前端与移动端体验

Web 端采用 Vue 3、TypeScript 和 Vite，已规划并接入家庭总览、成员档案、视觉扫描、人工复核、用药安全、计划、图谱、助手、大屏、授权、知识和模型实验室等十二个视图。界面强调本地状态、授权范围、证据来源、确认状态和降级信息的可见性，并具备主题切换、键盘导航、骨架屏、确认对话框和一定的无障碍测试覆盖。

移动端的价值在于将日常查看、提醒处理、身份登录和长辈模式延伸到更便携的场景。现有移动端任务已涉及会话生命周期、错误恢复、能力探测、高对比度、大字号、多家庭切换和 Android 安全配置，但不少工作仍待真机、WebView、PWA 和 TalkBack 验收。跨端体验不能只看页面是否能打开，更要验证授权切换、网络异常、会话过期和敏感数据遮蔽是否一致。

## 4. 技术架构与工程质量评估

系统由 Vue Web 前端、FastAPI 统一业务 API、MySQL 事实主库、事件与投影机制、视觉任务与质量检查、知识检索、本地模型适配和异步 outbox 等部分组成。前端不直接连接数据库、向量库或模型服务；服务端统一处理权限、事务、规则和证据校验。这种边界划分合理，有利于防止不同页面各自绕过权限或重复实现业务规则。

仓库拥有单元、集成、浏览器端到端、安全与可访问性相关测试，需求追踪矩阵也要求提交、PR、自动测试、人工验收和环境证据共同构成状态依据。这种“证据先于口头完成”的做法是项目较成熟的地方。

但工程质量仍有三个需要正视的限制。第一，部分需求状态依旧是进行中、待验收或阻塞，文档和代码存在不完全同步的风险。第二，正式会话持久化、轮换、CSRF 等生产认证能力尚未闭环，开发阶段的 `X-Actor-Id` 不能用于真实部署。第三，视觉和模型相关能力缺少获批固定集、独立评估和正式发布证据，不能用合成或局部测试替代真实验收。

## 5. 主要风险与改进方向

| 风险领域 | 当前判断 | 建议方向 |
|---|---|---|
| 生产身份与会话 | Web/PIN/人脸相关切片已有实现，但会话持久化、轮换、CSRF 和完整人工验收未闭环 | 将生产认证作为上线前阻断项，完成安全存储、过期、撤销、限流、CSRF 与渗透回归 |
| 健康数据授权 | 家庭边界和授权基线已具备，字段可见性与跨端一致性仍需持续验证 | 为授权创建统一回归矩阵，覆盖跨家庭、撤权后缓存、页面直链、导出和助手引用 |
| 视觉识别 | 流程与降级设计较完整，真实数据、独立评估和正式模型发布受阻 | 先完成数据授权与固定集，再定义拒识率、误匹配率、复核时长等验收指标 |
| 风险提醒 | 规则和预算思路明确，完整规则覆盖与严重告警验证不足 | 建立规则用例库，特别验证严重风险零漏报、重复提醒合并和升级链路 |

## 6. 后续建议与优先级

### P0：先完成可信使用的底座

1. 完成正式认证与会话治理。替换开发身份头，处理密码/PIN/人脸凭据的安全存储、速率限制、会话撤销、轮换、CSRF 和审计；没有这部分，不应进入真实家庭数据试用。
2. 关闭授权与事件中心的验收链路。以“创建家庭、授予字段权限、录入事件、撤权、投影更新、审计查询”为一条真实 API E2E 主链，覆盖 Web 和移动端。
3. 建立发布门禁看板。把需求矩阵中的“实现中”“待验收”“阻塞”连接到责任人、PR、CI、测试报告、环境与人工签署，避免仅因代码存在就误判交付状态。

### P1：提升核心闭环的可靠性

1. 为视觉链路建立可发布的评估体系。完成数据来源授权、脱敏与留存规则，冻结训练/验证/测试集；报告识别准确度之外的拒识率、冲突率、人工修正率、端到端耗时及弱网表现。
2. 把风险与计划的业务规则做成可审查资产。每条规则应明确输入字段、版本、严重程度、解释文案、测试样例和变更审批记录；对 HIGH 与 URGENT 级别进行单独回归。
3. 完成助手的证据闭环。回答中展示引用来源与版本，权限变更后立即重新过滤上下文；对无证据、模型离线、危险医疗问题和越权请求建立固定回归集。

### P2：完善体验与可运维性

1. 进行真实设备与可访问性验收。覆盖 Android 真机、PWA、WebView、屏幕阅读器、320px 小屏、特大字号、减少动效和低网络条件。
2. 建立可观测性和演练制度。记录请求 ID、授权拒绝、任务失败、规则版本、模型版本和降级原因；定期执行备份恢复、离线启动、依赖不可用和回滚演练。
3. 统一文档状态。README、页面说明、需求矩阵、模型卡和报告中应使用同一套状态词汇，并在版本更新时自动检查链接、测试结果和证据是否过期。

## 7. 结语

HomeCare Twin 最值得坚持的方向，是把智能能力放在受控流程之内：先保护家庭数据与授权边界，再保证事实可确认、规则可解释、结果可回溯，最后才扩展视觉模型和助手体验。后续工作的重点不应继续堆叠页面或模型概念，而应集中关闭认证、授权、事件、真实评估、跨端验收和运维演练这些决定系统是否可信的关键缺口。

本报告依据仓库当前代码、README、API 说明和需求追踪矩阵整理；其中“已验证”“进行中”“待验收”“阻塞”等判断以矩阵记录为准，不将演示实现等同于生产交付。

## 8. 系统架构分层解读

项目的架构重点不是把所有能力堆在一个服务中，而是将家庭事实、派生关系、确定性规则和语言解释分开。这样的分层可以减少模型输出直接影响健康记录的风险，也方便把权限、审计和版本信息放在统一的业务入口中处理。

家庭事实层保存成员、授权、健康事件、药品、计划和审计记录。它只接收人工确认、人工修正或符合业务契约的手工录入，不把模型的猜测直接保存为事实。该层是后续所有页面、规则和检索能力的依据。

关系投影层根据已确认的事实生成成员、药品、成分、过敏史、计划和照护者之间的关联。投影不是第二套事实库，出现异常时应可以从事件历史重新构建。图谱页面展示的节点和边也应遵循当前操作者的授权范围。

确定性规则层负责把明确的事实转换为风险提示和照护任务。规则引擎应保持可测试、可版本化和可解释，不能由语言模型在运行时修改。每个风险输出需要关联触发事实、规则版本、等级、时间和处理状态。

语言解释层负责检索、摘要、澄清和通俗表达。它只消费经过权限过滤的事实、规则结果和文档片段，并返回可定位的引用。该层不负责诊断、处方、停药、换药或调整剂量，也不允许绕过业务 API 直接读取底层数据。

| 分层 | 主要输入 | 主要输出 | 关键约束 |
|---|---|---|---|
| 家庭事实层 | 人工录入、确认结果、授权操作 | 不可覆盖的健康事件与审计 | 不保存未经确认的模型猜测 |
| 关系投影层 | 已确认事件 | 成员状态与关系图 | 可重建，不反向修改事实 |
| 规则层 | 当前事实与规则版本 | 风险、任务、告警预算结果 | LLM 不能改写规则结论 |
| 解释层 | 已授权事实、规则、知识片段 | 带引用的说明与摘要 | 无证据、越权和医疗决策请求必须受控降级 |

## 9. 关键业务数据流

一个较完整的药品录入链路可以概括为：图片采集、质量检查、文件上传、视觉任务、候选融合、人工复核、健康事件、状态投影、风险计算、计划任务和证据解释。任何一个环节失败都不应通过伪造成功状态掩盖问题。

第一步是采集。用户通过拍照或选择图片提供输入，前端在本地展示预览，并向后端请求质量检查。质量不通过时应只给出重拍提示，不创建后续任务；质量通过也只表示图片适合处理，不代表已经识别出药品。

第二步是候选产生。OCR、条码、包装区域和主数据等信息共同产生候选。候选之间一致时可以进入匹配状态；信息冲突、无可信匹配或置信度不足时，必须以冲突、未知或待复核状态呈现。

第三步是人工复核。复核者可以确认、修正或拒绝候选。系统应记录原始预测、修正后的值、修改原因、操作人、操作时间以及模型或融合配置版本。只有确认后的结果才允许生成正式事件。

第四步是事实与任务传播。健康事件写入后，投影刷新成员当前状态，规则层重新计算风险并生成待办。前端展示风险时应同步展示证据和确认入口；助手调用相关工具时也只能使用同一套已确认事实。

第五步是持续审计。若授权被撤销、事件被补偿或文件被删除，相关页面、派生投影、检索索引和缓存都要按照既定策略同步更新。删除和撤权不是单一按钮动作，而是一条需要跨模块验证的传播链路。

```text
采集文件
  -> 质量门控
  -> OCR / 条码 / 包装特征
  -> 候选融合与四状态判断
  -> 人工确认、修正或拒绝
  -> 追加健康事件
  -> 状态投影与规则计算
  -> 风险卡、计划任务、图谱和证据型解释
```

## 10. 角色与权限场景

家庭管理员负责创建家庭空间、维护成员、配置授权，并在需要时管理 PIN 或人脸凭据。管理员角色不意味着可以忽略审计和二次确认，尤其在查看高敏感字段、删除数据或变更凭据时仍需保留操作记录。

被照护成员是健康事实的重要确认主体。系统界面应清晰告诉其哪些信息将被记录、哪些成员拥有查看权限、授权何时到期，以及如何撤销或调整授权。对于人脸模板、检查报告等敏感信息，应强调同意、删除和留存边界。

照护者或子女只能在授权范围内处理任务。系统不应将“家庭成员”默认等同于“可查看全部健康信息”，也不能通过空状态、计数或错误文案泄露未获授权字段的存在。

系统维护者负责部署、监控、升级和故障处理。维护者应能查看脱敏的运行状态、任务失败和版本信息，但不应因运维身份自动获得家庭健康正文。生产环境应通过角色和流程将技术运维与健康内容访问分离。

| 角色 | 典型操作 | 权限风险 | 建议控制 |
|---|---|---|---|
| 家庭管理员 | 建成员、授权、配置凭据 | 误授权、误删除、共享设备 | 二次确认、审计、可撤销的授权记录 |
| 被照护成员 | 确认事实、查看自身记录 | 不理解数据用途 | 清晰同意说明与可见范围提示 |
| 照护者/子女 | 查看被授权事实、处理任务 | 跨成员或过期访问 | 成员/字段/动作/用途/期限联合校验 |
| 运维人员 | 部署、查看健康状态、故障恢复 | 通过日志或后台越权 | 脱敏日志、最小权限、操作留痕 |

## 11. 数据治理与隐私分析

家庭健康数据应遵循最小必要原则。页面、接口、日志、搜索结果和导出文件均只返回完成当前操作所需的最小字段。对于高敏感内容，除授权判断外，还需要考虑展示时机、遮罩、二次确认和截图泄露风险。

项目采用本地优先的部署理念。家庭版的 API、数据库、文件、视觉 OCR、向量索引和本地模型应位于家庭局域网或机构内网，网络出口默认拒绝。天气适配器若需要访问外部服务，也只能传输城市或区县编码等非健康正文信息。

原图、视频、文档、向量索引和缓存属于不同类型的数据资产。数据库事实是唯一事实主库；向量索引和图谱属于可重建的派生数据；模型登记用于描述制品和指标，不能反向覆盖健康事实。不同资产应有独立的留存、删除、备份和恢复策略。

删除权的实现需要特别谨慎。删除家庭或对象时，应明确事实记录、原始文件、索引切片、缓存、导出文件和备份中的处理方式。对于离线灾备，不应假装可以立即改写历史备份，而应记录墓碑、停止恢复已删除数据，并在恢复流程中执行过滤。

建议建立数据分类表，将成员标识、授权记录、健康事件、影像文件、OCR 文本、模型特征、知识文档和运行日志分别标记敏感级别、保存位置、访问角色、留存期限和删除方式。这样可以让新增功能在接入前明确数据责任，而不是上线后再补救。

## 12. 安全设计与威胁面

身份认证、人脸凭据和 PIN 是项目最敏感的入口。开发阶段可以使用 `X-Actor-Id` 加速联调，但生产环境必须替换为真实认证。会话令牌应具备安全存储、到期、撤销、轮换和异常登录处置能力，敏感操作还应使用挑战或二次确认。

文件上传需要防止恶意格式、伪造 MIME、超大文件、路径穿越、压缩炸弹和含有脚本的文档。视觉任务只应读取经过验证和隔离的文件，错误信息不能暴露服务器路径、稳定文件摘要或内部密钥。

授权绕过是第二类高风险问题。攻击者可能尝试修改家庭 ID、成员 ID、游标、导出范围、助手问题或前端缓存来获取未授权内容。因此权限校验必须在服务端的每一条资源访问路径执行，不能依赖前端隐藏按钮。

模型与检索还会带来提示词注入、引用伪造、跨成员上下文污染和危险建议等风险。助手应只调用白名单工具，工具返回的数据先经过授权过滤；回答生成后还需要检查引用是否真实存在、是否属于当前会话范围，以及是否包含被禁止的医疗决策内容。

建议将以下情况定义为发布阻断项：跨家庭或字段越权、撤权后仍可通过缓存读取数据、未确认药品进入风险计算、严重案例漏报、危险医疗建议、引用伪造、删除传播失败、默认网络出口放行，以及敏感数据进入普通日志。

## 13. 测试策略与验收口径

项目的测试不应只有组件渲染和接口返回成功两种类型。家庭照护系统的关键在于失败时能否安全降级、授权变化后能否正确隐藏数据、人工修正后能否完整保留证据、模型离线后能否避免产生虚假结论。

单元测试适合覆盖事件状态机、候选融合、风险规则、告警预算、计划安全时间窗、权限谓词和页面状态转换。此类测试应快速运行，并在每次代码提交时执行。

集成测试适合覆盖数据库迁移、事务、投影重建、文件上传、向量权限、外部适配器和异步任务。尤其需要验证 SQLite 开发环境与 MySQL 环境的差异，避免只在本地内存环境中通过。

契约测试应固定 OpenAPI、请求参数、错误码、幂等键、分页游标、版本字段和身份头的行为。前后端使用同一契约可以减少“页面存在但接口语义变化”的联调问题。

端到端测试应覆盖成功和失败路径。成功路径包括扫描、复核、事件、风险、计划和助手解释；失败路径包括图片质量差、候选冲突、无授权、服务不可用、会话到期、撤权、删除和模型离线。

| 测试层级 | 关注对象 | 代表性验证 |
|---|---|---|
| 单元测试 | 规则、状态机、权限谓词 | 冲突候选不能自动入库；严重风险不受普通预算压制 |
| 集成测试 | 数据库、文件、任务、投影 | 事件补偿后状态可重建；删除传播到派生存储 |
| 契约测试 | API Schema、错误码、幂等 | 前后端对超时、401、分页和版本字段理解一致 |
| E2E 测试 | 用户闭环 | 上传、复核、风险、任务、授权撤销全链可用 |
| 安全测试 | 越权、恶意输入、出口 | 跨家庭拒绝；提示词注入不泄露数据；文件被隔离 |
| 可访问性测试 | 键盘、对比度、读屏、小屏 | 长辈模式在 320px 与特大字号下仍能完成关键操作 |

视觉链路的评估不应只看单个模型指标。仓库测试方案已给出 OCR-first 的目标口径，例如良好图像条码解码率、未知 SKU 转人工复核率、自动通过结果精确率、字段来源区域完整率和 CPU 单图全流程 P95 等。后续报告这些指标时必须同时提供样本量、数据来源、硬件、置信区间和失败案例，不能只给一个百分比。

助手的评估也需要独立进行。建议固定盲测集，分别统计意图路由、工具选择、Schema 合法、引用存在、无证据拒答、越权拒绝和危险医疗请求拒绝等指标。模型参数变更、知识库更新或提示词修改后，应自动重跑同一批用例。

## 14. 可观测性、运维与部署建议

系统上线后最常见的问题并非单一代码异常，而是某个依赖离线、数据迁移不完整、模型版本与规则版本不匹配、缓存未刷新或授权变更未及时传播。因此，日志、指标和追踪需要围绕业务链路设计，而不只是记录 HTTP 状态码。

每个请求建议携带请求 ID，并关联操作人、家庭范围、资源类型、授权结论、事件版本和错误码。日志中应避免记录健康正文、PIN、原始人脸模板、完整令牌和未脱敏文档内容。

关键指标可包括 API 成功率、P50/P95 响应时间、视觉任务队列长度、OCR/条码失败率、人工复核等待时长、风险规则执行耗时、助手拒答率、授权拒绝数、删除任务完成率和离线降级次数。指标需要按版本和环境维度观察，避免把开发环境问题误判为生产问题。

部署应有基础档和增强档的明确边界。基础档在本地模型、视觉或天气依赖不可用时，仍应支持家庭、成员、事件、规则和人工确认等核心能力；增强档可以接入额外模型，但不能成为核心安全流程的唯一依赖。

建议定期演练以下场景：数据库恢复、服务重启、网络出口阻断、Ollama 离线、向量索引损坏、视觉任务失败、授权撤销、模型回滚和家庭删除。演练结果应形成版本、时间、责任人、步骤和问题清单，而不是只保留口头结论。

## 15. 产品体验与信息架构建议

家庭总览页应优先回答近期变化、待确认事项、风险依据和可见范围四个问题。用户进入系统后不应先面对复杂功能菜单或聊天框，而应先知道当前是否存在需要处理的照护事项。

成员档案页应将事实、来源、确认状态、更新时间和可见范围放在同一上下文中。字段被隐藏时，只显示“未获授权”，不要额外提示隐藏字段的具体内容或数量。

视觉扫描页应明确区分图片质量通过、候选识别成功和正式事实确认三个阶段。许多用户会把“上传成功”误认为“药品已入库”，页面需要使用清晰的状态文字和下一步操作避免误解。

人工复核页应突出原始证据、候选差异、冲突原因和修改影响。确认或修正按钮不应放在缺乏上下文的位置，提交前应让用户清楚知道此次操作会生成何种事件，以及后续会影响哪些风险或计划。

风险页的重点是解释，而不是制造焦虑。每张风险卡建议显示等级、触发原因、证据、规则版本、建议处理人和当前状态。一般提醒可合并为摘要，高等级风险需要有单独的确认和升级路径。

助手页应避免塑造成“万能医生”。其界面应始终提示回答基于哪些已确认事实、规则和文档；缺少证据时应明确说明无法确认，而不是生成看似流畅但无依据的建议。

大屏和图谱适合展示脱敏的聚合信息、趋势和待办状态。它们不应成为展示健康正文或人脸凭据的窗口，尤其在家庭公共空间使用时应默认隐藏敏感细节。

## 16. 建议的三阶段迭代路线

第一阶段目标是完成可信基础链路。重点包括正式认证、会话治理、家庭与字段授权、事件追加与投影、撤权传播、审计记录和基础档离线降级。完成条件是关键链路能在真实 API 环境中稳定复现，且越权、撤权和会话到期场景有自动化证据。

第二阶段目标是完成可用的照护闭环。重点包括视觉质量门控、人工复核、风险规则、告警预算、计划确认、照护升级、知识文档和引用型助手。完成条件是使用合规固定集和可复现环境，端到端流程能展示成功、冲突、未知、离线和人工修正等完整状态。

第三阶段目标是提升可靠性和可推广性。重点包括模型治理、困难样本闭环、真实设备验证、可访问性验收、性能基准、备份恢复、监控告警和受控部署。完成条件是每项能力都有明确版本、指标、失败案例、回滚路径和人工验收记录。

| 阶段 | 优先目标 | 核心产出 | 不应跳过的验收 |
|---|---|---|---|
| 第一阶段 | 安全与事实底座 | 认证、授权、事件、审计 | 越权、撤权、会话、恢复和真实 API E2E |
| 第二阶段 | 照护业务闭环 | 复核、规则、计划、助手 | 冲突/未知处理、证据展示、离线降级 |
| 第三阶段 | 质量与发布准备 | 评估、运维、跨端体验 | 固定集、性能、真机、备份恢复和回滚 |

## 17. 团队协作与交付管理建议

建议将每一项任务绑定需求编号、负责人、代码提交、PR、自动化测试、人工验收、环境信息和风险说明。对于模型、数据集和安全相关变更，还应绑定数据卡、模型卡或威胁模型更新记录。

需求追踪矩阵应成为状态的唯一入口。README、演示文档和汇报材料可以引用矩阵，但不要各自维护“完成度”，否则很容易出现同一能力在不同文档中状态不一致的问题。

代码评审应特别关注权限判定位置、错误状态、敏感字段日志、删除与缓存、模型输出边界和测试是否覆盖失败路径。页面样式、组件重构和文案调整可以分开提交，避免业务安全变更混入大规模视觉改动而难以审查。

对于阻塞项，应明确阻塞原因、解除条件和临时边界。例如真实数据集未获批时，可以继续维护合成测试和接口契约，但不得将模型标记为已发布；正式会话未完成时，可以演示开发身份流程，但不得宣称支持生产登录。

每次迭代结束建议召开短周期证据复盘，逐项确认哪些能力“已验证”、哪些只是“代码完成”、哪些仍“待人工验收”。复盘应记录遗漏的失败场景和下一轮需要补充的测试，而不是只汇总完成数量。

## 18. 提交前检查清单

- 文档中的功能状态是否与需求追踪矩阵一致。
- 新增接口是否通过权限、参数、错误码和幂等性检查。
- 写入事实的操作是否保留操作者、时间、来源、版本和修正原因。
- 视觉结果是否只有在人工确认后才进入正式风险计算。
- 助手是否只使用已授权数据，并给出真实可定位的引用。
- 页面是否展示网络离线、模型不可用和无权限等降级状态。
- 敏感日志、截图、测试夹具和示例文件是否已脱敏。
- 删除或撤权是否覆盖数据库、文件、索引、缓存和导出路径。
- Web 与移动端是否验证了会话到期、家庭切换和小屏显示。
- README、接口文档、模型卡和测试报告是否同步更新。
- 需要人工验收的项目是否明确列出环境、设备、版本和验收人。

## 19. 综合评价

HomeCare Twin 的核心竞争点不应定义为“使用了多少 AI 技术”，而应定义为是否能把 AI 限制在可信流程里。项目已经在架构、需求、测试和页面设计中建立了较清晰的边界：模型负责候选、检索和解释；人工负责确认和修正；规则负责风险判断；事件和审计负责追溯。

从工程实践角度看，项目的长处是问题拆分细、文档体系完整、对失败和降级有明确考虑。短板则集中在将这些设计证据真正收敛为已验证交付，特别是数据集批准、生产认证、真实环境回归、模型评估和跨端人工验收。

后续应避免为了展示效果而放松未知结果的复核门槛，也不要为了增加功能而引入未经审查的云端依赖。把授权、事实、规则、证据和回滚机制做扎实，才能让视觉识别和助手能力成为项目的增益，而不是新的不确定来源。
