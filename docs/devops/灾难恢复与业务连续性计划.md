# 灾难恢复与业务连续性计划

> 本文档是家健镜系统灾难恢复与业务连续性的完整计划，覆盖风险评估、恢复策略、恢复流程、演练计划。

## 1. 概述

### 1.1 目标

1. 最小化停机时间：RTO < 4 小时
2. 最小化数据丢失：RPO < 1 小时
3. 保障业务连续：核心功能优先恢复
4. 明确责任：每个环节有负责人
5. 定期演练：每季度一次演练

### 1.2 关键指标

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| RTO | 4 小时 | 恢复时间目标 |
| RPO | 1 小时 | 恢复点目标 |
| 可用性 | 99.9% | 年停机 < 8.76 小时 |
| 数据完整性 | 100% | 无数据丢失 |

### 3.3 备份验证

```bash
#!/bin/bash
# 每月备份验证脚本

echo "=== 备份验证 $(date) ==="

# 1. 检查备份文件存在
BACKUP_FILE="/backup/db_latest.sql.gz"
if [ ! -f "$BACKUP_FILE" ]; then
  echo "错误：备份文件不存在"
  exit 1
fi

# 2. 检查备份文件大小
SIZE=$(stat -c%s "$BACKUP_FILE")
if [ "$SIZE" -lt 1000000 ]; then
  echo "错误：备份文件过小"
  exit 1
fi

# 3. 恢复测试
echo "恢复测试..."
docker exec postgres psql -U postgres -c "CREATE DATABASE restore_test;"
gunzip -c "$BACKUP_FILE" | docker exec -i postgres psql -U postgres -d restore_test

# 4. 验证数据
TABLE_COUNT=$(docker exec postgres psql -U postgres -d restore_test -t -c "SELECT count(*) FROM information_schema.tables WHERE table_schema='public';")
echo "恢复表数量: $TABLE_COUNT"

# 5. 清理
docker exec postgres psql -U postgres -c "DROP DATABASE restore_test;"

echo "=== 验证完成 ==="
```

## 4. 恢复流程

### 4.1 故障检测

```
监控系统告警
    ↓
运维人员确认
    ↓
判断故障等级
    ├─ P0（系统不可用）→ 启动灾难恢复
    ├─ P1（核心功能异常）→ 启动应急响应
    └─ P2（非核心异常）→ 常规处理
```

### 4.2 数据库恢复

```bash
#!/bin/bash
# 数据库恢复脚本

BACKUP_FILE=$1
TARGET_TIME=$2

echo "=== 数据库恢复 ==="

# 1. 停止应用
docker-compose stop backend worker

# 2. 备份当前数据库（如果可能）
pg_dump homecare > /backup/corrupt_$(date +%Y%m%d).sql

# 3. 恢复全量备份
gunzip -c "$BACKUP_FILE" | psql -U homecare homecare

# 4. 应用 WAL 到目标时间点（PITR）
if [ -n "$TARGET_TIME" ]; then
  pg_restore --time="$TARGET_TIME"
fi

# 5. 验证数据
psql -U homecare -c "SELECT count(*) FROM medicines;"

# 6. 启动应用
docker-compose start backend worker

# 7. 健康检查
curl -f http://localhost:8000/health

echo "=== 恢复完成 ==="
```

### 4.3 站点切换

```bash
#!/bin/bash
# 主备切换脚本

echo "=== 站点切换 ==="

# 1. 停止主站点
ssh primary "docker-compose stop"

# 2. 确认数据同步完成
ssh standby "pg_isready"

# 3. 提升备站点为主
ssh standby "pg_ctl promote"

# 4. 更新 DNS
aws route53 change-resource-record-sets   --hosted-zone-id Z1234567890   --change-batch file://dns-change.json

# 5. 验证
sleep 60
curl -f https://api.homecare.com/health

echo "=== 切换完成 ==="
```

### 4.4 恢复优先级

```
第一阶段（0-1小时）：
- 数据库恢复
- 用药提醒服务
- 基础 API 服务

第二阶段（1-4小时）：
- 所有 API 服务
- 数据同步服务
- 推送通知服务

第三阶段（4-8小时）：
- 健康助手服务
- 视觉识别服务
- 统计报表服务

第四阶段（8-24小时）：
- 完整功能验证
- 数据一致性校验
- 性能优化
```

## 5. 应急响应团队

### 5.1 角色职责

| 角色 | 职责 | 联系人 |
| --- | --- | --- |
| 总指挥 | 整体协调和决策 | 技术负责人 |
| 运维负责人 | 基础设施恢复 | 运维工程师 |
| 数据库负责人 | 数据库恢复 | DBA |
| 开发负责人 | 应用恢复 | 后端负责人 |
| 通信负责人 | 内部和外部沟通 | 产品经理 |

### 5.2 沟通机制

- 故障发生后 15 分钟内成立应急小组
- 每 30 分钟同步一次进展
- 恢复后 24 小时内完成故障复盘
- 3 个工作日内提交改进计划
