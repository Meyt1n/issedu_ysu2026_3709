# HCT-201 OCR 字段提取契约 V1

> 状态：设计基线。本文定义药品包装字段的证据格式和处理边界，不代表 OCR、条码或药品身份确认能力已经完成。

## 1. 目标与边界

药品录入采用 OCR-first（OCR 主链路）方案：用户主动摆放药盒并点击拍照，系统先对整张受控图片进行质量检查和 OCR，再使用 YOLO 作为包装/条码区域辅助定位，使用专用条码解码器读取商品码或追溯码，最后由规则、本地药品主数据和受约束的本地 LLM 完成字段归类与核对。

本契约不允许：

- 用整盒图像分类器直接宣称“这是某个药品”；
- 让 YOLO 类别覆盖每个 SKU，或用 YOLO 结果覆盖 OCR/条码原始证据；
- 让 LLM 补写图片中不存在的文字、猜测批号/有效期或替换原始 OCR；
- 把字段抽取称为计算机视觉语义分割。这里的 LLM 能力是文本候选的语义解析/槽位填充，不是像素级分割；
- 在没有人工确认的情况下，把结果写入正式健康状态或触发用药规则。

## 2. 处理顺序

```text
用户拍照
→ OpenCV 质量门控与必要的透视/旋转校正
→ 全图 OCR，保存文字框、原始值和 OCR 置信度
→ YOLO 辅助定位包装与条码区域（失败时不阻塞全图 OCR）
→ 条码/二维码专用解码，OCR 只作为码值兜底
→ 规则、单位/日期/批号格式和本地词典生成字段候选
→ 本地 LLM 只在已有候选中做字段归类和规范化
→ 条码、OCR、包装类型和本地主数据交叉核对
→ MATCHED / CONFLICT / UNKNOWN / REVIEW
→ 人工确认或修正后再写入 health_event
```

YOLO 只负责回答“包装或条码大致在哪里”，OCR 负责回答“图片上写了什么”，条码解码器负责回答“编码内容是什么”，LLM 负责回答“已有证据更像哪个字段”。四者不能互相伪造证据。

## 3. 字段责任矩阵

| 字段 | 首选来源 | 辅助来源 | 进入确认前的最低要求 |
|---|---|---|---|
| `drug_name` 药名 | OCR 文本框 | 本地药品词典、条码主数据 | 有原始 OCR 文本和来源区域；不能只靠图像分类 |
| `specification` 规格 | OCR 文本框 | 单位/剂量规则、主数据 | 能定位原始文本；保留 `mg`、`ml`、`片` 等单位 |
| `manufacturer` 厂家 | OCR 文本框 | 厂家词典、主数据 | 不能把品牌名自动当厂家名 |
| `batch_number` 批号 | OCR 文本框 | 批号格式规则、条码解析 | 低质量或多个候选时必须 `REVIEW` |
| `expiry_date` 有效期 | OCR 文本框 | 日期规则、条码解析 | 保留原始日期写法和规范化日期；无法确定日/月时不得补齐 |
| `product_or_trace_code` 商品码/追溯码 | 条码/二维码解码 | OCR 码值兜底 | 记录码制、原始码值、解码质量和来源区域 |
| `package_type` 包装类型 | YOLO/规则 | 用户修正 | 至少有包装类别证据；不作为药品身份唯一依据 |

## 4. 原始证据格式

原始 OCR 和条码结果必须先落入受控证据对象，再进行字段抽取。示例字段如下：

```json
{
  "region_id": "r12",
  "source_type": "ocr",
  "raw_value": "阿莫西林胶囊 0.5g×24粒",
  "polygon": [[100, 80], [420, 80], [420, 140], [100, 140]],
  "ocr_confidence": 0.94,
  "model_version": "paddleocr-local-v1",
  "image_id": "img-01"
}
```

每个最终字段必须至少包含：

```json
{
  "value": "阿莫西林胶囊",
  "raw_value": "阿莫西林胶囊",
  "source_region_ids": ["r12"],
  "confidence": 0.91,
  "model_versions": {
    "region_detector": "yolo-assist-v1",
    "ocr": "paddleocr-local-v1",
    "barcode_decoder": "zxing-cpp-v1",
    "extractor": "local-llm-schema-v1"
  },
  "status": "REVIEW"
}
```

`confidence` 必须由系统依据 OCR/解码质量、规则匹配、多次拍摄一致性和主数据核对结果计算。不能直接信任 LLM 自报的置信度。所有字段都必须允许 `null`、`UNKNOWN` 和 `REVIEW`。

## 5. LLM 使用规则

LLM 输入只包含已授权的 OCR token、条码解析结果、包装候选和必要的本地主数据候选。输出必须通过固定 JSON Schema，并提供 `source_region_ids` 或 `source_token_ids`。

LLM 可以：

- 将已有 OCR 候选归入药名、规格、厂家、批号或有效期字段；
- 对日期、单位、大小写和空格做可逆规范化；
- 标记候选冲突、证据不足和需要人工确认的原因。

LLM 不可以：

- 生成输入证据中不存在的新文字；
- 在 OCR 与条码冲突时自行选择一个并标记为已确认；
- 将“可能是”转成正式药品身份；
- 修改、删除或覆盖原始 OCR/条码记录；
- 输出诊断、处方、停药、换药或剂量判断。

## 6. 数据标注要求

HCT-201 不要求为每个字段训练一个 YOLO 类别。数据应优先保存：

1. 包装对象框：`medicine_box`、`medicine_bottle`、`blister_pack`；
2. 条码/二维码区域框：`barcode_region`；
3. OCR 文本框或多边形及其原始转写；
4. 可选字段角色：`drug_name`、`specification`、`manufacturer`、`batch_number`、`expiry_date`；
5. 反光、遮挡、模糊、倾斜、裁切和手写等困难属性。

`drug_name_region`、`spec_region` 和 `expiry_region` 可以作为辅助预标注，但不是 YOLO 发布模型的必需类别；OCR 自身的文本检测框才是字段来源的主要证据。

## 7. 确认状态

| 状态 | 条件 | 行为 |
|---|---|---|
| `MATCHED` | OCR、条码、包装和主数据没有关键冲突 | 仍需人工确认后进入正式事实 |
| `CONFLICT` | 药名、规格、日期、条码或主数据相互矛盾 | 禁止自动入库，展示各来源证据 |
| `UNKNOWN` | 无法匹配本地主数据或字段证据不足 | 允许保存待复核任务，不生成药品事实 |
| `REVIEW` | 低质量、多个候选、关键字段缺失或模型不可用 | 请求重新拍照或人工修正 |

## 8. 发布验收

- [ ] 原始 OCR token、文本框、条码解码结果和版本信息可追溯；
- [ ] YOLO 不可用时，全图 OCR 仍能走到受控的结构化结果或明确降级；
- [ ] LLM 无法从无证据输入生成字段，字段输出全部通过 Schema；
- [ ] OCR 与条码冲突进入 `CONFLICT`，不能自动入库；
- [ ] 每个字段可展示原始值、来源区域、系统计算置信度和模型版本；
- [ ] 人工修正保留 before/after、原因、操作者、时间和训练同意状态；
- [ ] 真实健康数据、原始图片、模型权重和未审计数据不进入 Git、Issue、PR 或日志。
