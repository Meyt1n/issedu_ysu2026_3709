# ADR-002: 采用事件溯源架构

## 状态

已采纳

## 背景

家健镜系统需要完整记录家庭成员的健康操作历史，支持数据追溯、审计和状态重建。传统的 CRUD 模式只保留当前状态，丢失了历史变更信息。

## 决策

采用事件溯源（Event Sourcing）+ CQRS 架构：

1. **写模型**：所有状态变更以事件形式追加存储，不可修改
2. **读模型**：通过订阅事件构建投影，用于高效查询
3. **事件存储**：health_events 表存储所有事件
4. **状态重建**：通过重放事件恢复任意时间点的状态

## 理由

### 为什么选择事件溯源

1. **完整审计**：所有操作有记录，可追溯
2. **时间旅行**：可重建任意时间点的状态
3. **调试友好**：问题可通过事件序列复现
4. **天然同步**：事件是多端同步的理想载体
5. **业务洞察**：事件数据可用于分析和优化

### 为什么选择 CQRS

1. **读写分离**：写操作和读操作各自优化
2. **读模型灵活**：可为不同查询场景构建不同投影
3. **扩展性好**：读写可独立扩展

## 后果

### 正面

- 完整的操作历史
- 可追溯和审计
- 支持时间点查询
- 事件驱动架构，解耦好

### 负面

- 学习曲线陡峭
- 最终一致性（读模型有延迟）
- 事件 schema 演进复杂
- 需要处理事件版本兼容

## 替代方案

1. **传统 CRUD + 审计日志**：简单但历史不完整
2. **只做审计表**：保留历史但不可重建状态
3. **时间戳数据库**：如 Datomic，但技术栈不匹配

## 实施要点

- 事件不可变，只能追加
- 事件有版本号，支持 schema 演进
- 投影可重建，不存储业务逻辑
- 重要操作有幂等性保证
- 事件存储有备份和归档策略

---

*ADR-002 记录了事件溯源架构决策，为系统数据一致性和可追溯性提供基础。*
