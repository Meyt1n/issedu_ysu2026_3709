# ADR-013-后端技术栈选型与架构决策

> 本文档是家健镜系统后端技术栈选型与架构决策的架构决策记录，覆盖决策背景、候选方案、评估维度、最终决策和实施计划。

## 1. 决策背景

### 1.1 问题陈述

家健镜系统后端需要选择合适的技术栈，支撑用户管理、健康数据、用药提醒、在线问诊、商城等多个业务模块。需要在开发效率、性能、可维护性、团队熟悉度之间取得平衡。

### 1.2 约束条件

1. 团队技能：团队成员熟悉 Python，有 FastAPI 开发经验
2. 性能要求：支持 10 万日活，P99 响应 < 500ms
3. 开发周期：3 个月完成 MVP
4. 可扩展性：支持微服务拆分
5. 生态成熟：需要完善的 ORM、认证、测试工具

### 1.3 时间线

- 2026-07-01：提出技术栈选型需求
- 2026-07-10：完成候选方案调研
- 2026-07-15：技术评审会议
- 2026-07-20：最终决策

## 2. 候选方案

### 2.1 Python + FastAPI

**简介**：基于 Python 的现代 Web 框架，使用 Starlette 和 Pydantic，原生支持异步。

**优点**：
- 开发效率高，代码简洁
- 原生异步支持，性能优秀
- 自动生成 OpenAPI 文档
- Pydantic 数据验证
- 团队熟悉 Python
- AI/ML 生态丰富（健康数据分析）
- 部署简单

**缺点**：
- Python 性能不如 Go/Java
- 多线程受 GIL 限制
- 类型提示非强制
- 大型项目需要严格规范

**适用场景**：快速迭代、AI 集成、中小规模系统。

### 2.2 Java + Spring Boot

**简介**：企业级 Java 框架，生态成熟，功能全面。

**优点**：
- 生态最成熟，企业级方案完善
- 性能稳定，适合高并发
- 强类型，安全可靠
- 微服务支持好（Spring Cloud）
- 人才储备充足

**缺点**：
- 开发效率较低，代码冗长
- 启动慢，内存占用高
- 团队不熟悉 Java
- AI/ML 集成不如 Python
- 配置复杂

**适用场景**：大型企业系统、高并发交易系统。

### 2.3 Go + Gin/Gin

**简介**：Go 语言 Web 框架，高性能，轻量级。

**优点**：
- 性能优秀，接近 C
- 编译型，部署简单
- 并发模型优秀（goroutine）
- 内存占用低
- 云原生友好

**缺点**：
- 团队不熟悉 Go
- 生态不如 Python/Java 成熟
- 错误处理冗长
- 泛型支持较新
- AI/ML 生态弱

**适用场景**：高并发网关、微服务、云原生应用。

### 2.4 Node.js + NestJS

**简介**：基于 TypeScript 的 Node.js 框架，借鉴 Angular 架构。

**优点**：
- TypeScript 类型安全
- 前后端语言统一
- 异步非阻塞，I/O 密集型性能好
- 模块化架构清晰
- 开发效率高

**缺点**：
- CPU 密集型性能差
- 回调地狱（已改善）
- 团队不熟悉 TypeScript
- 生态不如 Python 丰富
- 内存管理需要注意

**适用场景**：实时应用、I/O 密集型、全栈团队。

## 3. 评估维度

### 3.1 评估矩阵

| 维度 | 权重 | Python/FastAPI | Java/Spring | Go/Gin | Node/NestJS |
| --- | --- | --- | --- | --- | --- |
| 开发效率 | 25% | 9 | 6 | 7 | 8 |
| 性能 | 20% | 7 | 8 | 9 | 7 |
| 团队熟悉度 | 20% | 9 | 4 | 3 | 5 |
| 生态成熟度 | 15% | 8 | 9 | 7 | 8 |
| AI/ML 集成 | 10% | 10 | 5 | 4 | 6 |
| 可维护性 | 10% | 7 | 9 | 8 | 8 |
| **加权总分** | **100%** | **8.35** | **6.65** | **6.35** | **7.15** |

### 3.2 关键考量

1. **AI 集成需求**：健康数据分析、医学影像识别、智能问答等功能需要深度集成 AI 模型，Python 生态无可替代。
2. **团队技能**：团队核心成员有 Python 和 FastAPI 经验，学习成本最低。
3. **开发周期**：3 个月 MVP 需要快速迭代，Python 开发效率最高。
4. **性能评估**：10 万日活对 Python 来说完全可以胜任，通过异步和水平扩展可满足需求。

## 4. 最终决策

### 4.1 决策结果

**选择 Python + FastAPI 作为后端主要技术栈。**

### 4.2 决策理由

1. **AI 生态优势**：健康数据分析、医学影像、智能问答等核心功能依赖 Python AI 生态（PyTorch、scikit-learn、OpenCV）。
2. **开发效率**：FastAPI 代码简洁，自动文档，Pydantic 验证，能在 3 个月内完成 MVP。
3. **团队匹配**：团队熟悉 Python，无需额外学习成本。
4. **性能够用**：异步支持 + 水平扩展可满足 10 万日活需求。
5. **部署简单**：Docker 容器化部署，运维成本低。

### 4.3 补充方案

- **高性能网关**：如果后续需要更高性能的 API 网关，可考虑用 Go 单独开发。
- **实时通信**：WebSocket 使用 FastAPI 原生支持，配合 Redis 发布订阅。
- **异步任务**：使用 Celery + Redis/RabbitMQ 处理耗时任务。

## 8. 风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
| --- | --- | --- | --- |
| Python 性能瓶颈 | 中 | 中 | 异步处理、缓存、水平扩展、关键服务用 Go 重写 |
| 团队规范不统一 | 高 | 中 | 制定代码规范、Code Review、自动化检查 |
| 依赖版本冲突 | 中 | 低 | 使用 pip-tools 锁定版本、定期更新 |
| 数据库性能 | 中 | 高 | 索引优化、读写分离、分库分表预案 |

## 9. 决策审查

### 9.1 审查节点

- MVP 上线后 1 个月：评估性能和开发效率
- 上线后 3 个月：评估是否需要微服务拆分
- 每季度：回顾技术栈适用性

### 9.2 成功指标

1. API P99 响应 < 500ms
2. 系统可用性 > 99.9%
3. 新功能开发效率符合预期
4. 团队满意度 > 4/5
5. 无重大技术债务
