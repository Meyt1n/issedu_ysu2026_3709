# ADR-0003：家庭 Owner 管理员权限边界

- 状态：已接受，合并前由维护者完成最终复核
- 日期：2026-08-07
- 决策人/复核人：Meyt1n；merge 记录为人工复核证据
- 关联需求、Issue、PR：FR-01、FR-03、NFR-01、NFR-02；Issue #16；PR #10
- 替代/被替代：细化 ADR-0002 的成员授权规则，不替代本地可信域、默认不出网和人工确认原则

## 背景与当前事实

P0 API 需要区分家庭 Owner 与被 Owner 授权的非 Owner 照护者。家庭 Owner 是该家庭的管理责任主体；非 Owner 照护者只能依据成员、字段、动作和有效期授权访问。若只按“子女/照护者”名称推断权限，会把 Owner 的明确管理员权限误报为越权，或错误放宽非 Owner 访问。

## 决策驱动因素

- Owner 需要管理自己家庭的成员目录、健康事件和当前状态；
- 非 Owner 访问必须遵循最小权限、字段级可见范围、动作、目的和有效期；
- 不能跨家庭读取、修改或推断健康数据；
- 健康数据默认本地保存，授权判定必须可测试、可审计、可撤回；
- 合并流程不设置额外第二人 approval，维护者 merge 即代表完成代码与风险人工复核。

## 候选方案

### 方案 A：Owner 管理员 + 非 Owner 细粒度授权（采用）

Owner 对自己家庭的成员目录、健康事件和状态拥有显式管理员权限；非 Owner 照护者只有授权字段、动作、目的和有效期内的访问。优点是符合家庭管理边界且能支持子女协同；代价是需要明确 Owner 判定、越权测试、审计和撤权测试。

### 方案 B：所有角色统一按字段授权

Owner 也必须逐字段授予自身权限。该方案边界形式统一，但会让家庭创建、成员管理和紧急撤权流程复杂化，不能表达 Owner 对家庭本身的管理责任，因此不采用。

## 决策

1. 当前 P0 数据模型以 `Household.created_by` 承载 Owner 身份事实，不以显示角色名称猜测权限。若未来引入独立 `owner_id` 或多 Owner 模型，必须通过新迁移和替代 ADR 同步更新，不能只改字段名称。
2. Owner 只可访问自己所属家庭；在该家庭内，Owner 可以读取和管理成员目录、健康事件及状态投影，并受 API 响应字段和审计约束。
3. 非 Owner 必须同时满足成员范围、字段范围、动作、`X-Access-Purpose` 目的和有效期授权；撤权、过期或跨家庭访问立即拒绝。跨家庭和 ID 猜测采用统一隐藏式 `404`，详细原因只进入脱敏审计。
4. 授权变更和撤权使用 `expected_version` 乐观锁；授权生命周期及非 Owner 访问决定写入不含健康正文的 `access_audit`。
5. 任何未确认视觉识别结果仍不得进入正式健康状态、风险计算或药物计划；本 ADR 不削弱人工确认/修正的产品安全边界。
6. Relay Review Bot 的风险提示保留真实 P0/P1/P2；本项目不要求额外第二人 approval，维护者 merge 即代表人工复核完成。

## 后果

- 正向影响：Owner 的管理权限有明确事实源，非 Owner 的授权边界可测试、可审计，Bot 不再因角色名称误判 Owner 越权。
- 代价/新约束：所有读取接口都必须携带家庭边界和授权上下文；成员列表和健康字段必须分别测试。
- API、数据、授权、模型/规则/知识影响：API 必须返回明确的拒绝原因和字段范围；LLM/视觉模块不得绕过授权或确认状态。
- 必须补充的测试、监控和文档：Owner/非 Owner/跨家庭/撤权/过期/字段越权测试；同步 Story、API、领域模型和安全文档。

## 验证、复审与回滚

- 以 `tests/contract/test_p0_contract.py`、`tests/integration/test_event_chain.py` 和授权测试验证 Owner 与非 Owner 边界；
- 若实现无法证明家庭边界、字段过滤或撤权即时生效，禁止开放非 Owner 协同接口；
- 若团队后续改变 Owner 权限，新增 ADR 替代本 ADR，不直接改写历史结论；
- 合并前由维护者检查实现、测试、风险和回滚，merge 记录作为本次人工复核证据。
