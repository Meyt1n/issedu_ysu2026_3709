# ADR-0001：统一 FastAPI 业务入口与 MySQL 事实主库

- 状态：提议
- 日期：2026-08-02
- 决策人：待项目组启动评审确认
- 关联：FR-01、FR-02、FR-04、NFR-03

## 背景

HomeCare Twin 需要把成员授权、不可覆盖健康事件、当前状态、视觉人工确认、风险规则、计划和工具调用保持在同一事务与审计边界。若多个服务或前端直接写业务表，会出现授权不一致、事件与投影分裂以及模型结果绕过人工确认的问题。

新方案明确课程交付使用 Vue、FastAPI、MySQL 和本地 Ollama；P0 关系图规模有限，无需把 Neo4j 或向量库设为第二事实源。

## 提议

- FastAPI 是唯一业务 API 和数据库写入口；
- MySQL 8 是唯一事实主库，SQLAlchemy 2 与 Alembic 管理访问和迁移；
- `health_event` 追加写，outbox 在同一事务发布投影/规则任务；
- 家庭关系图使用 MySQL 可重建投影，P0 不引入 Neo4j；
- FAISS/Qdrant 只保存可重建向量和权限元数据引用；
- Vue、管理员端、CV/OCR、RAG 和 Ollama 不得直接修改业务表；
- 只有人工确认的识别结果可通过应用服务写入正式事件。

## 影响

优点：授权、事务、审计、事件和证据只有一个事实来源；基础档可在 AI 依赖离线时运行；投影/索引可重建和回滚。

代价：FastAPI 成为关键入口；异步任务需 outbox、幂等和重试；MySQL 的 JSON/并发/全文能力需在原型中验证；复杂图谱查询可能需要后续专用存储。

## 被否决的当前方案

- PostgreSQL/ChromaDB 作为默认基线：与新实施方案指定的 MySQL/FAISS-Qdrant 路线不一致，且八周内维护双数据库无必要。
- Flask/FastAPI 分别直写数据库：会复制授权、事务和规则边界。
- Neo4j 作为 P0 事实源：增加同步一致性与运维成本，当前规模没有证据支持。

## 接受条件

- Windows/Docker 上完成 MySQL 中文、时区、JSON、事务、迁移和备份恢复原型；
- 完成“人工确认 + 事件 + outbox + 投影”的原子性和失败恢复测试；
- 完成跨家庭、撤权和并发更新测试；
- 团队确认课程环境、资源和许可证；
- 评审通过后把状态改为“已接受”并链接实现证据。

## 回滚与演进

在尚无业务实现时可低成本改选兼容数据库；实现后必须通过仓储接口、迁移与数据导出迁移，不允许建立第二套绕过事件的写路径。只有复杂关系查询出现可测瓶颈时，才新建 ADR 评审 Neo4j，且仍保持 MySQL 为事实主库。
