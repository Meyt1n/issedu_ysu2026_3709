# ADR-0001：统一业务 API 与数据库基线

- 状态：提议
- 日期：2026-07-29
- 决策人：待项目组在启动评审中确认

## 背景

实训报告第 10-15 页建议 Flask 管理后台、FastAPI 高性能接口、MySQL 业务库和 ChromaDB
向量库。仓库正式方案需要先建立身份、家庭、授权和审计基线；如果 Flask 和 FastAPI 同时
直接访问业务表，容易出现两套权限与事务规则。

## 提议

- FastAPI 是唯一业务 API 和业务数据库访问入口；
- SQLAlchemy 2.x async 是 ORM 基线，Alembic 是唯一结构变更入口；
- PostgreSQL 16 是协作开发/部署基线，SQLite 只用于快速自动测试；
- 后续 Flask 管理端只能作为 API 客户端，不直接访问业务表；
- ChromaDB/Milvus 仅保存向量与权限元数据引用，不替代业务数据库。

## 影响

优点：

- JWT、RBAC、资源所有权和审计只有一个事实来源；
- 异步模型/RAG 编排与业务 API 使用同一套请求 ID 和错误契约；
- PostgreSQL 更适合后续 JSON、并发任务和细粒度索引。

代价：

- 报告中的 Flask-SQLAlchemy/MySQL 示例不会原样复刻；
- 管理端必须通过 API 联调；
- SQLite 与 PostgreSQL 的差异需要额外集成测试。

## 回滚

若课程验收强制要求 MySQL，可新增经过测试的 SQLAlchemy 驱动和迁移兼容层；若必须展示
Flask，可实现只调用 FastAPI 的独立管理端。不得让第二个服务绕过业务 API 直接修改表。

## 接受条件

- 完成 FastAPI/Flask 最小原型和职责边界评审；
- 完成 PostgreSQL/MySQL 课程兼容与运维成本对比；
- 验证 Windows、本地 CI 和演示环境可复现；
- 客户代表、开发、测试和资料组记录评审结论。

条件满足前，本文不构成已经实施的技术事实。
